Go 실무 패턴

2026년 11월 16일

  • Go
  • Backend
  • Design-Patterns
  • Performance

Go는 언어 기능이 적은 대신 관례가 코드 품질을 좌우한다. 실무에서 반복해서 효과를 본 관례는 하나의 생각으로 묶인다. 숨은 동작을 줄이고 계약을 타입과 시그니처에 드러내는 것이다. 에러, 인터페이스, 생성자, 의존성 그래프, 성능 튜닝이 모두 이 원칙을 따른다.

핵심

  • 에러는 문자열이 아니라 의미를 가진 값이다. 감쌀 때는 %w로 원인을 잃지 않고, 판단은 errors.Is와 errors.As로 체인 전체에서 한다. 바깥으로 나가는 계약은 도메인 에러 코드로 고정하고 HTTP 상태는 그 코드에서 정하며, 로그는 책임지는 계층에서 한 번만 남긴다. Go 에러 핸들링 전략 실무 가이드
  • 추상화는 쓰는 쪽이 정한다. 인터페이스는 소비자 패키지에 작게 두고, 함수는 인터페이스를 받아 구체 타입을 돌려준다. 그래야 테스트 더블을 넣기 쉽고 호출자는 실제 기능을 그대로 본다. 포인터 수신자 메서드만 있는 타입은 값으로는 인터페이스를 만족하지 못한다. Go 인터페이스 설계 원칙 - Accept Interfaces, Return Structs
  • 생성자는 꼭 필요한 것과 고를 수 있는 것을 구분한다. 필수 의존성은 인자로 강제하고, 선택 설정만 Functional Options로 받으며, 기본값은 생성자 안 한 곳에서만 정한다. 의존성이 많아지면 Wire처럼 코드를 생성하는 DI로 그래프를 컴파일 타임에 검증하고, Provider는 생성만 맡긴다. 옵션 함수 안에서 값을 검증하고(예: 0 이하 타임아웃 거부), 옵션끼리 충돌할 때의 규칙을 정한다. 모든 값을 옵션으로 내리면 필수값 계약이 무너진다. 이 패턴은 유연한 설정보다 생성자를 오래 버티게 하는 장치다. Wire를 활용한 Go 의존성 주입(DI) 구현
  • 성능은 측정 없이 고치지 않는다. pprof에서 flat이 높으면 함수 자체가, cum이 높으면 하위 호출이 문제이고, 가설은 하나씩 바꿔 전후 프로파일로 확인한다. pprof 엔드포인트는 내부망이나 인증 뒤에만 둔다. Go pprof를 활용한 성능 프로파일링 가이드
  • GC가 자주 도는 이유는 대개 파라미터가 아니라 할당 패턴이다. 할당을 먼저 줄이고, 컨테이너에서는 GOMEMLIMIT으로 상한을 정하고, GOGC는 마지막에 맞춘다. sync.Pool은 수명이 짧은 버퍼에만 쓴다. Go 가비지 컬렉터(GC) 이해와 튜닝 경험
