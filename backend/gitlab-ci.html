GitLab CI/CD는 GitLab에 내장된 CI/CD 도구다. 프로젝트 루트에 .gitlab-ci.yml을 두면 GitLab이 알아서 읽고, 푸시나 MR 같은 트리거가 생길 때마다 Stage와 Job으로 이뤄진 Pipeline을 만든다. 실제 Job은 GitLab 서버와 따로 도는 Runner가 실행한다.

왜 알아야 하나

코드가 저장소에 푸시될 때마다 빌드, 테스트, 배포를 자동으로 돌리고, 그 절차 전체를 저장소 안의 YAML 한 파일로 정의한다. 1편

다만 파일이 수백 줄로 커지면 관리가 어려워지고 4편, 시크릿을 아무 브랜치에서나 읽게 두면 보안 사고가 난다 2편. 그래서 기본 구조만큼이나 변수 관리, Runner 격리, 파일 분할, Job 제어를 같이 알아야 쓸 만한 파이프라인이 나온다.

작동 방식

Pipeline, Stage, Job

구성 요소역할
.gitlab-ci.yml파이프라인 정의 파일(프로젝트 루트)
Pipeline트리거로 만들어지는 Stage와 Job의 집합
StageJob을 묶어 실행 순서를 정하는 단계
Job독립된 환경에서 도는 실제 작업 단위
RunnerJob을 실행하는 에이전트

Job에서 꼭 있어야 하는 키는 script 하나다. Job 하나에 script 한 줄만 써도 파이프라인이 만들어진다. 같은 Stage의 Job은 병렬로 돌고, 다음 Stage는 이전 Stage의 Job이 모두 성공해야 시작한다. stages를 적지 않으면 .pre, build, test, deploy, .post가 기본값이다. 점(.)으로 시작하는 Job은 실행되지 않고 템플릿으로 쓰인다. after_script는 Job이 성공하든 실패하든 항상 돌기 때문에 정리 작업에 맞다. 1편

트리거는 브랜치 푸시(push), MR 생성·갱신(merge_request_event), 스케줄(schedule), UI 수동 실행(web), API 호출(api), 다른 파이프라인(trigger) 등이다. 문법은 CI Lint로 미리 검증할 수 있다. 디버그용 CI_DEBUG_TRACE는 시크릿을 포함한 모든 변수를 로그에 찍으므로 프로덕션에서는 조심해야 한다. 1편

변수와 시크릿

변수는 GitLab이 자동으로 주는 Predefined 변수(200개 이상), .gitlab-ci.yml에 쓰는 변수, UI에서 넣는 Project·Group·Instance 변수로 나뉜다. 민감한 값은 YAML에 쓰지 않고 UI에 넣는다. 2편

  • Protected 변수는 보호된 브랜치와 태그에서 도는 파이프라인에서만 읽힌다. feature/* 브랜치가 프로덕션 시크릿에 손대지 못하게 막는 장치다.
  • Masked 변수는 Job 로그에 [MASKED]로 찍힌다. 8자 이상, Base64에 쓰이는 문자만, 한 줄이어야 마스킹된다.
  • 같은 이름이 여러 곳에 있으면 Trigger 변수, 수동 실행 변수, 스케줄 변수, Job 변수, 전역 변수, Project, Group, Instance, Predefined 순으로 앞쪽이 이긴다.
  • Job 사이에 실행 중 계산한 값(빌드 버전, 태그 등)을 넘길 때는 dotenv 아티팩트를 쓴다.
  • kubeconfig, 서비스 계정 JSON, SSH 키, TLS 인증서처럼 큰 값은 File 타입 변수로 둔다.
  • 외부 저장소로는 HashiCorp Vault(Premium 이상은 네이티브 통합, 무료로는 JWT 인증)와 AWS Secrets Manager를 연동할 수 있다.

Runner와 Executor

Runner는 범위에 따라 Shared(인스턴스 전체), Group, Project로 나뉜다. Executor는 Job이 어떤 환경에서 도는지 정한다. 3편

Executor격리 수준용도
Shell없음간단한 스크립트, 호스트 직접 접근
Docker컨테이너일반적인 CI/CD
Docker MachineVM + 컨테이너오토스케일링
KubernetesPod클라우드 네이티브
VirtualBoxVM완전한 격리가 필요할 때

Job과 Runner는 태그로 짝을 맞추고, 태그 없는 Job을 받을지는 Runner의 run_untagged로 정한다. 동시 실행 수는 전체 한도(concurrent)와 Runner별 한도(limit)로 조절하고, 캐시는 S3 같은 분산 캐시로 Runner끼리 나눠 쓸 수 있다. 3편

선택지와 트레이드오프

이미지 빌드: DinD와 소켓 바인딩

일반 Docker Executor 안에는 Docker 데몬이 없어 docker 명령을 쓸 수 없다. 이미지를 빌드하는 방법은 두 가지다. 3편

특성Docker-in-Docker소켓 바인딩
격리완전 격리호스트와 공유
보안안전호스트에 접근 가능
성능약간 느림빠름
캐시와 레이어Job마다 초기화, 매번 다운로드호스트 캐시 활용

DinD는 TLS를 켜는 것이 기본이자 권장이다. TLS를 끄면 통신이 암호화되지 않으므로 테스트 용도로만 쓴다. 소켓 바인딩은 호스트 Docker에 바로 닿기 때문에 신뢰할 수 있는 코드만 돌려야 한다. Shell Executor도 격리가 없어 같은 주의가 필요하다. 3편

파이프라인 나누기

패턴용도키워드
include같은 프로젝트 안에서 설정 파일 분리include: local/project/remote/template
Parent-Child동적 파이프라인, 조건부 실행trigger: include:
Multi-Project다른 프로젝트 파이프라인 트리거trigger: project:
동적 생성런타임에 Child YAML 생성아티팩트 + trigger

Child를 트리거하는 Job에 strategy: depend를 주면 Child가 끝날 때까지 Parent Job이 기다린다. 없으면 Parent Job은 바로 끝나고 Child는 비동기로 돈다. 모노레포에서는 rules:changes로 바뀐 파일이 있는 쪽의 Child만 띄운다. 4편

Job 제어: rules, needs, dependencies

rules는 only/except를 대체한다. 위에서 아래로 평가해 처음 맞는 규칙을 적용하고, 맞는 규칙이 없으면 Job은 돌지 않는다. 조건은 if, changes, exists이고, when으로 on_success(기본), always, never, manual, delayed를 고른다. workflow:rules는 Job이 아니라 파이프라인 자체를 만들지 정하며, MR이 열려 있을 때 브랜치 파이프라인을 건너뛰어 중복 실행을 막는 데 쓴다. 5편

특성needsdependencies
실행 순서제어함(DAG)제어 안 함
아티팩트기본으로 가져옴이것만 제어
Stage 무시가능불가능

needs를 쓰면 프론트엔드 빌드가 끝나자마자 백엔드 빌드를 기다리지 않고 프론트엔드 테스트가 시작된다. needs: [job]이 그 Job의 아티팩트까지 가져오므로 dependencies가 따로 필요 없는 경우가 많다. 재사용은 extends로 Job 전체를 상속하거나(나중 값이 앞의 값을 덮는다) !reference로 script 같은 키만 골라 가져온다. 5편

외부 시스템과 묶기

외부에서 파이프라인을 돌리는 방법은 토큰 기반 Pipeline Trigger, Webhook, GitLab API(생성, 상태 조회, Job 재시도, 취소)다. 파이프라인 안에서 GitLab API를 부를 때는 임시 토큰인 CI_JOB_TOKEN을 쓰고, 어느 프로젝트가 이 토큰으로 접근할 수 있는지는 Token Access 설정에서 정한다. 정기 실행은 Scheduled Pipeline(cron)으로 건다. Slack 알림과 배포 승인 같은 ChatOps, Jenkins나 GitHub Actions에서 GitLab 파이프라인을 부르는 연동도 가능하다. 6편

GitOps 도구와 함께 쓸 때 원칙은 CI는 아티팩트를 만들고 CD는 GitOps 에이전트가 맡는다는 것이다. 원문은 CI Job이 argocd app sync로 직접 Sync하는 예와, CI는 이미지만 빌드해 푸시하고 ArgoCD Image Updater가 새 태그를 감지해 배포하는 예를 함께 보여 준다. 자세한 내용은 GitOps에 있다. 6편
