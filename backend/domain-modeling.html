도메인 모델링은 비즈니스 규칙이 지켜지도록 상태를 바꾸는 길을 몇 개로 좁히는 설계다. 규칙은 데이터 가까이에 두고, 금지된 연산은 검사하기보다 아예 호출할 수 없게 만든다. 객체 캡슐화, 타입으로 표현한 상태 기계, 덮어쓰지 않는 버전 저장이 같은 목표를 서로 다른 층에서 이룬다.

왜 필요한가

허용되지 않은 상태 변경이 어딘가에서 일어나면 버그가 생긴다. getter와 setter만 있는 빈약한 모델이나 여러 서비스가 상태를 제각기 바꾸는 구조에서는 규칙이 코드 곳곳에 흩어진다. 상속 계층이 깊어지면 변경 비용이 크게 늘어난다. 이력이 중요한 도메인에서 기존 값을 덮어쓰면 감사 추적이 깨진다.

그래서 OOP의 네 축(추상화, 캡슐화, 상속, 다형성)을 외우는 것보다 상태 일관성을 지키는 것이 실무에서 더 중요하다. OOP는 패턴 암기가 아니라 모델 경계를 설계하는 일이다.

작동 방식

규칙을 데이터 옆에 둔다

필드를 직접 열지 않고 메서드가 불변 조건을 지킨다. 객체는 만들어질 때부터 유효해야 한다. 은행 계좌라면 잔액을 바깥에서 고칠 수 없게 막고, 생성 시 초기 잔액이 음수면 거부하며, 입금은 양수만, 출금은 잔액 안에서만 허락한다. 책임이 큰 객체는 애그리거트로 나눈다.

금지된 연산은 API에서 없앤다

상태는 enum으로, 전이는 좁은 메서드로 표현하고 내부 상태는 비공개로 둔다. 외부 입력은 경계에서 한 번만 도메인 타입으로 파싱한다. 검사기는 우회할 수 있지만, 존재하지 않는 생성자나 메서드는 호출할 수 없다. 다만 잔고 같은 동적 조건은 여전히 런타임 검증이 필요하다.

보여 주는 상태와 통제하는 상태를 나눈다

여러 변수로 된 상태 그래프를 단계(phase) 하나로 투영하면, 같은 단계라도 가드 조건이 다른 상태가 하나로 합쳐진다. 투영된 전이는 “어딘가에서는 허용된다”는 뜻일 뿐이고, 잔고 같은 수치 가드는 남지 않는다. 투영은 진단용으로만 쓰고, 실제 실행을 통제하려면 전체 구체 상태를 유지하며 그 상태에서 가능한 전이만 허락한다.

이력은 덮어쓰지 않고 쌓는다

Append-only 버저닝은 기존 문서를 고치지 않고 새 버전을 추가한다. 저장은 모든 버전을 담는 documents와 최신 버전만 캐시하는 current_documents로 나눠 감사 추적과 조회 성능을 함께 얻는다. 쓰기는 한 트랜잭션 안에서 다음 순서로 한다.

flowchart LR
    A[최신 버전 조회] --> B["새 버전 생성<br/>version + 1"]
    B --> C[documents insert]
    C --> D[current_documents upsert]
    D --> E[audit log 기록]

(uri, version) 유니크 인덱스는 필수이고, 최신 조회용으로 (uri, updated_at) 인덱스를 둔다. 소프트 삭제도 새 버전(DELETED 상태)으로 표현한다. 히스토리 압축과 아카이빙 정책은 미리 정한다. 핵심은 “무조건 저장”이 아니라 일관된 버전 생성 규칙이다. 쓰기 경로를 하나로 모으고 트랜잭션으로 묶으면 감사성과 복구성이 좋아진다.

선택지와 트레이드오프

선택얻는 것대가와 주의점
메서드로 불변 조건 강제규칙이 한 곳에 모이고 결합도가 준다책임이 커지면 애그리거트를 나눠야 한다
깊은 상속 계층공통 동작 재사용변경 비용이 크게 늘어난다
타입과 좁은 전이 메서드금지된 연산을 호출할 수 없다잔고 같은 동적 조건은 런타임 검증이 따로 필요하다
단계 하나로 투영상태를 한눈에 진단수치 가드가 사라져 실행 통제 근거로 쓸 수 없다
Append-only 버저닝감사 추적, 복구저장소가 둘이 되고 인덱스, 압축, 아카이빙 정책이 필요하다
데코레이터로 동작 덧붙이기원본 수정 없이 기능 조합숨은 동작이 늘어 디버깅이 어려워진다

데코레이터라는 말은 두 가지를 가리킨다. 디자인 패턴의 Decorator는 객체를 감싸 로깅, 캐시, 인증 같은 기능을 원본 수정 없이 붙인다. TypeScript 데코레이터는 클래스와 메서드에 메타데이터나 동작을 주입하는 언어 기능이고, 여러 개를 달면 표현식은 위에서 아래로 평가되고 적용은 아래에서 위로 된다. 둘은 이름만 같고 목적이 다르다. 어느 쪽이든 보이지 않는 동작이 늘어나면 테스트와 문서화 규칙이 반드시 따라와야 한다. 공통 관심사는 미들웨어나 인터셉터로 대신할 수 있는지 먼저 보고, 데코레이터 기반 DI나 validation은 팀 숙련도가 없으면 유지보수 비용이 크다.

실제 적용

  • 타입과 상태 설계는 주문, 승인처럼 허용 전이가 분명한 상태 기계와, 화폐처럼 단위와 스케일이 중요한 값에 특히 잘 맞는다.
  • 투영과 전체 상태를 구분하는 원칙은 명세에서 lint나 상태 소유자 코드를 생성할 때 적용한다.
  • Append-only 버저닝에서 자주 하는 실수는 세 가지다. 최신 컬렉션만 유지하고 히스토리 정합성을 검증하지 않는 것, 버전 생성 로직을 여러 서비스가 중복 구현하는 것, 업데이트 도중 audit 기록을 빠뜨리는 것이다.
