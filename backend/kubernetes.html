Kubernetes는 컨테이너 워크로드를 선언형으로 운영하는 플랫폼이다. 사용자가 원하는 상태를 API Server에 등록하면, 컨트롤러가 현재 상태를 관찰해 그 상태로 맞춘다. 워크로드, 네트워킹, 설정과 시크릿, 서비스 메시, 오토스케일링, 보안이 모두 이 원리 위에 올라가 있다.

왜 컨트롤러부터 봐야 하나

Kubernetes의 모든 동작은 컨트롤러 패턴이다. kubectl apply로 Deployment를 만들어도 실제 Pod를 만드는 것은 Deployment Controller다. 모든 컨트롤러는 현재 상태를 관찰하고 원하는 상태와 비교해 차이를 메우는 Reconciliation Loop를 돈다. 1편

이 루프는 Level-triggered 방식이다. “상태가 바뀌었다”는 사건이 아니라 “지금 상태가 이렇다”를 기준으로 움직인다. 그래서 컨트롤러가 재시작돼도 현재 상태를 다시 읽고 정상적으로 조정을 이어 간다. 1편

Deployment는 Pod를 직접 다루지 않고 ReplicaSet을 거친다. 업데이트하면 새 ReplicaSet이 생기고 maxSurge, maxUnavailable 한도 안에서 Pod가 조금씩 옮겨 간다. 롤백은 새 ReplicaSet을 만드는 것이 아니라 기존 ReplicaSet을 다시 늘리는 동작이다. 남겨 둘 ReplicaSet 수는 revisionHistoryLimit(기본 10)으로 제한하며, 너무 많으면 etcd 부담이 커진다. 1편

StatefulSet은 Pod 이름이 app-0, app-1처럼 순서대로 붙고, 0부터 차례로 만들고 역순으로 지운다. Headless Service로 Pod마다 고정 DNS를 받고, Pod를 지워도 PVC는 남아서 mysql-0이 다시 뜨면 같은 데이터를 쓴다. 순서가 필요 없고 빠른 스케일링이 중요하면 podManagementPolicy: Parallel을 쓴다. CronJob은 concurrencyPolicy로 겹치는 실행을 허용(Allow, 기본), 건너뛰기(Forbid), 교체(Replace) 중에서 고른다. 1편

서비스 네트워킹

Pod는 만들어질 때마다 IP가 바뀐다. Service는 그 앞에 안정적인 엔드포인트를 둔다. ClusterIP는 클러스터 내부 가상 IP, NodePort는 모든 노드에 같은 포트를 연다(그 노드에 Pod가 없어도 다른 노드의 Pod로 넘긴다). LoadBalancer는 NodePort에 클라우드 LB를 자동으로 붙인 것이고, ExternalName은 외부 주소를 DNS CNAME으로 돌려준다. 2편

실제 패킷 라우팅은 kube-proxy가 규칙을 만들어 처리한다. iptables는 조회가 O(n), IPVS와 nftables는 O(1)이다. 원문은 IPVS 모드가 향후 deprecated될 예정이라는 공식 문서를 근거로, 새 클러스터에는 nftables(1.33 Stable) 또는 iptables 모드를 권한다. Headless Service는 ClusterIP 없이 DNS 조회에 Pod IP 목록을 그대로 돌려주므로 StatefulSet, gRPC 같은 클라이언트 측 로드밸런싱, 서비스 디스커버리에 쓴다. Pod가 수천 개인 Service에서는 EndpointSlices가 엔드포인트를 최대 100개씩 나눠 바뀐 조각만 갱신한다. 2편

설정과 시크릿

ConfigMap은 설정을 이미지에서 떼어 낸 평문 설정이고, Secret은 Base64 인코딩일 뿐 암호화가 아니다. 둘 다 크기 한도는 1MB다. Secret은 etcd 저장 암호화(EKS라면 AWS KMS Envelope Encryption)를 켜야 하고, 쓰지 않는 ServiceAccount 토큰 자동 마운트는 끈다. 3편

시크릿을 클러스터 밖 저장소에 두는 방법은 두 가지다. 3편

볼륨으로 마운트한 파일은 자동으로 갱신되지만, 앱이 파일을 캐시하거나 환경변수로 받았다면 Pod를 재시작해야 바뀐 값이 반영된다. 3편

선택지와 트레이드오프

서비스 메시

재시도, 타임아웃, 서킷 브레이커, mTLS를 서비스마다 구현하는 대신 서비스 메시가 인프라 계층에서 처리한다. Istio는 컨트롤 플레인 istiod와 각 Pod에 자동 주입되는 Envoy 사이드카로 이뤄진다. Gateway는 외부 트래픽 진입점, VirtualService는 경로·헤더·가중치 기반 L7 라우팅(카나리, A/B 테스트), DestinationRule은 subset, 로드밸런싱, 서킷 브레이커 같은 트래픽 정책을 맡는다. mTLS는 PeerAuthentication에서 DISABLE, PERMISSIVE(마이그레이션용), STRICT로 정한다. 4편

실전 예로, Route 53 와일드카드 레코드와 ACM 와일드카드 인증서, ALB, Istio 와일드카드 Gateway를 한 번 묶어 두면 새 서비스는 VirtualService 하나만 추가하면 된다. DNS나 인증서 작업이 필요 없다. 503이 나면 DestinationRule subset 라벨과 Pod 라벨 불일치, 포트 설정, mTLS 모드 불일치부터 본다. 4편

오토스케일링

축대상도구
수평Pod 개수HPA, KEDA
수직Pod 리소스(CPU/Memory)VPA
클러스터Node 개수Cluster Autoscaler, Karpenter

HPA는 autoscaling/v2가 stable이고, 메트릭을 여러 개 걸면 가장 많은 replica를 요구하는 메트릭을 따른다. Pod에 resource requests가 없으면 HPA는 작동하지 않는다. VPA는 별도로 설치해야 한다. HPA와 VPA를 같은 CPU/Memory 메트릭에 동시에 걸면 서로 반대로 움직이며 충돌하므로, HPA는 요청 수나 큐 길이 같은 Custom/External 메트릭, VPA는 Off 모드로 추천만 받는 조합을 권한다. 5편

노드 쪽은 Kubernetes SIG Autoscaling이 공식 지원하는 Cluster Autoscaler와 Karpenter 중에서 고른다. Cluster Autoscaler는 Node Group을 미리 정의해야 하고 여러 클라우드를 지원한다. Karpenter는 제약 조건만 주면 워크로드에 맞는 인스턴스를 직접 골라 더 빨리 띄우고, Disruption으로 노드를 자동 최적화한다. KEDA는 HPA를 확장해 60개 이상의 이벤트 트리거를 지원하고, HPA와 달리 0까지 줄일 수 있으며 Cron 스케줄링도 된다. 5편

보안

계층도구핵심
인증·인가RBACRole, ClusterRole, 최소 권한
네트워크NetworkPolicyingress/egress 제어, Zero Trust
워크로드Pod Security StandardsPrivileged/Baseline/Restricted
IDServiceAccountIRSA, 토큰 마운트 제어

RBAC는 Role·RoleBinding(네임스페이스)과 ClusterRole·ClusterRoleBinding(클러스터)으로 권한을 나눈다. 기본 ClusterRole 중 view는 Secret을 볼 수 없고, edit는 RBAC를 바꿀 수 없다. NetworkPolicy는 CNI 플러그인이 지원해야 작동한다. Calico, Cilium, Weave Net은 지원하지만 AWS VPC CNI 단독으로는 안 된다. podSelector와 namespaceSelector를 같은 - 아래 쓰면 AND, 따로 쓰면 OR이 되고, NetworkPolicy가 뜻대로 작동하지 않을 때 흔한 원인은 CNI 미지원, 셀렉터 라벨 오타, egress에서 DNS(UDP 53)를 허용하지 않은 경우다. Pod Security Admission은 1.25에서 GA가 됐고 PodSecurityPolicy를 대체했으며, enforce, audit, warn 모드로 적용한다. 6편
