GitOps

2026년 11월 19일

  • GitOps
  • Kubernetes
  • DevOps

GitOps는 Git을 Single Source of Truth(SSOT)로 삼는 운영 방식이다. 원하는 시스템 상태를 Git에 선언하고, 클러스터 안의 에이전트가 그 상태를 끌어와 실제 상태와 계속 맞춘다. 대표 도구는 ArgoCD와 Flux이고, 실제로 쓰려면 환경별 설정, 시크릿, CI 연동, Progressive Delivery까지 함께 정해야 한다.

왜 필요한가

전통적인 CI/CD에서는 Jenkins나 GitHub Actions 같은 CI가 빌드와 테스트를 마친 뒤 kubectl apply나 helm upgrade로 클러스터에 직접 배포한다. 동작은 하지만 근본적인 문제가 네 가지 있다. 1편

문제내용
Credential 분산CI 서버가 프로덕션 클러스터에 접근하는 강한 권한을 갖는다
Drift 감지 불가누가 kubectl edit으로 직접 고치면 Git과 실제 상태가 어긋난다
Audit Trail 부재누가, 언제, 왜 바꿨는지 추적하기 어렵다
복잡한 롤백되돌리려면 어떤 버전이 배포돼 있었는지부터 찾아야 한다

CI 서버가 뚫리면 공격자가 프로덕션에 임의 코드를 배포할 수 있다는 점이 가장 큰 위험이다. GitOps는 배포 권한을 CI에서 떼어 내고, 모든 변경을 Git 커밋으로 남겨 이 문제를 푼다.

작동 방식

네 가지 원칙

2021년 CNCF 산하 OpenGitOps 프로젝트가 정리한 원칙은 네 가지다. 1편

  1. Declarative: “Pod 3개를 만들어라”가 아니라 “Pod가 3개인 상태여야 한다”를 기술한다. Kubernetes 자체가 선언적 시스템이고, GitOps는 이 철학을 Git과 묶은 것이다.
  2. Versioned and Immutable: 커밋은 불변이고 전체 히스토리가 남는다. 감사 추적, git revert 롤백, 규제 산업의 감사 요구 대응이 여기서 나온다.
  3. Pulled Automatically: Git에 변경이 올라가면 에이전트가 알아서 감지해 적용한다.
  4. Continuously Reconciled: 한 번 적용하고 끝내지 않고 Reconciliation Loop로 계속 비교한다. 누가 replicas를 5개로 바꿔도 Git에 정의된 3개로 되돌린다. 이것이 Self-Healing이다.

GitOps 에이전트는 Kubernetes Controller 패턴을 한 단계 위에서 구현한 것이다. 원하는 상태가 YAML의 Spec 대신 Git 저장소에 있고, 변경 감지가 etcd watch 대신 Git polling이나 Webhook으로 이뤄진다는 점만 다르다. 1편

Push 모델과 Pull 모델

관점Push(전통 CI/CD)Pull(GitOps)
네트워크 방향외부 → 클러스터클러스터 → Git
필요 권한CI에 cluster-admin 수준 kubeconfig에이전트에 클러스터 내부 권한, Git은 읽기 전용
공격 표면CI 서버가 뚫리면 클러스터도 위험Git 저장소 보호에 집중
방화벽인바운드 허용 필요아웃바운드만 허용

ArgoCD와 Flux도 클러스터 안에서는 강한 권한을 갖는다. 그래도 공격 경로가 Git 저장소 하나로 모여 보안 관리가 단순해진다. 1편

CI와 CD를 나눈다

GitOps에서는 CI가 이미지 같은 아티팩트를 만들고, 클러스터 반영은 GitOps 에이전트가 맡는다. CI는 클러스터에 직접 접근하지 않는다. 이렇게 나누면 배포 권한은 클러스터 안 에이전트에만 있고, 감사 기록은 Git 커밋 히스토리에 남고, 롤백은 재빌드 없이 git revert로 끝난다. 6편

CI가 이미지를 푸시한 뒤 매니페스트를 갱신하는 방법은 세 가지다. CI가 GitOps 저장소에 직접 커밋하거나, PR을 만들어 리뷰와 테스트를 거친 뒤 반영하거나, CI는 이미지만 푸시하고 에이전트가 새 태그를 찾아 매니페스트를 갱신한다. 원문은 뒤의 두 방식을 권장한다. 마지막 방식이 ArgoCD Image Updater와 Flux Image Automation이다. Image Updater의 write-back을 argocd 방식으로 두면 변경이 Git에 남지 않아 GitOps 원칙에 어긋나므로, 프로덕션에서는 git 방식을 쓴다. 6편

선택지와 트레이드오프

ArgoCD와 Flux

ArgoCD는 API Server(Web UI, CLI, Webhook), Repo Server(Git clone과 매니페스트 렌더링), Application Controller(Reconciliation Loop)로 이뤄진다. 배포 단위는 Application CRD이고, Sync Waves와 Hooks(PreSync, Sync, PostSync, SyncFail)로 적용 순서와 시점을 제어하며, ApplicationSet으로 템플릿 하나에서 여러 Application을 만든다. prune: true를 켜면 Git에서 지운 리소스가 클러스터에서도 바로 지워지므로, 파일을 실수로 지우면 프로덕션 리소스가 사라질 수 있다. 2편

Flux는 GitOps Toolkit이라는 독립 컨트롤러 묶음이다. Source Controller가 Git, Helm, OCI에서 아티팩트를 가져오고, Kustomize Controller와 Helm Controller가 적용하며, Notification Controller가 알림을 주고받고, Image Automation이 이미지 태그 갱신을 맡는다. 필요한 컨트롤러만 골라 설치할 수 있고 설정은 모두 CRD로 관리한다. 3편

관점ArgoCDFlux
구조하나로 설치하는 애플리케이션독립 컨트롤러 모음
UI강력한 내장 Web UICLI 중심, UI는 별도
멀티 클러스터중앙 ArgoCD가 관리클러스터마다 Flux 설치
이미지 자동 갱신Image Updater(별도 프로젝트)내장
SOPS플러그인네이티브

UI, 중앙 집중 관리, 복잡한 Sync 전략이 중요하면 ArgoCD, 경량화, 이미지 자동 갱신, SOPS, 클러스터별 독립성이 중요하면 Flux가 맞다. 3편

Kustomize와 Helm

같은 앱을 dev, staging, prod에 배포하면 replicas, 리소스, DB 호스트, 로그 레벨, 도메인이 환경마다 다르다. 환경별로 YAML을 통째로 따로 두면 중복이 쌓이고 변경이 빠진다. 그래서 공통 부분과 환경별 차이를 나눈다. 4편

도구장점단점맞는 곳
Kustomize순수 YAML, 배우기 쉬움, kubectl 내장, Git diff가 분명함조건부 로직이 약함내부 앱, 단순한 환경 차이
Helm강력한 템플릿, 패키지화, 의존성 관리, 생태계렌더링해야 보이므로 디버깅이 어려움써드파티 소프트웨어, 복잡한 로직
둘을 함께(post-rendering)양쪽 장점복잡도 증가Helm 차트에 레이블 추가, 차트가 지원하지 않는 설정 패치, 조직 표준 강제

내부 앱은 Kustomize, 인프라 컴포넌트는 Helm으로 나누는 방식이 흔하다. 4편

시크릿

Kubernetes Secret의 Base64는 인코딩이지 암호화가 아니고, Git 히스토리에 한 번 들어가면 영구히 노출된다. Git을 SSOT로 두면서 비밀을 지키는 방법은 세 가지다. 5편

방법Git에 두는 것장점단점
Sealed Secrets클러스터 키로 암호화한 SealedSecret단순하고 외부 의존성이 없음클러스터에 묶임, 키 로테이션 시 전부 재암호화, 컨트롤러 키 유출 시 전부 복호화
External Secrets Operator외부 저장소를 가리키는 참조Git에 비밀 값이 없음, 중앙 관리, 자동 로테이션외부 서비스 의존, 네트워크 지연, 비용
SOPS값만 암호화한 파일키는 평문이라 Git diff가 의미 있음, 같은 키로 멀티 클러스터로테이션이 수동

단일 클러스터로 빨리 시작하려면 Sealed Secrets, 클라우드에서 중앙 관리가 필요하면 ESO, Flux로 멀티 클러스터를 운영하면 SOPS와 age가 맞다. 5편

배포 전략

전략다운타임리소스롤백 속도위험 노출
Recreate있음낮음느림높음
Rolling없음일시 증가중간중간
Blue-Green없음2배빠름낮음
Canary없음약간 증가빠름낮음

Progressive Delivery는 Argo Rollouts나 Flagger로 한다. Argo Rollouts는 Deployment를 대신해 Blue-Green과 Canary를 제공하고, AnalysisTemplate으로 메트릭을 보고 자동 롤백한다. Flagger는 Flux와 함께 쓰며 Istio, Linkerd, NGINX Ingress 등과 붙는다. 6편
