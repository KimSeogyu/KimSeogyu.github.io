Enterprise Go

Enterprise Go

2026년 11월 19일

  • Go
  • Backend
  • Architecture

Enterprise Go는 팀에서 오래 운영할 Go 서비스의 책임 경계와 운영 규칙을 한곳에 모은 실무 기준이다. 프레임워크나 라이브러리를 먼저 고르기보다, 구조를 어디서 나누고 장애 때 어떻게 멈출지를 팀 표준으로 고정한다.

왜 필요한가

Go는 표준 라이브러리만으로도 서버를 띄울 수 있다. 팀이 커지면 문제는 코드를 짜는 속도가 아니라, 사람마다 미들웨어 순서와 트랜잭션 경계와 재시도 정책이 달라지는 쪽이다. 진입점에서 조립과 종료를 모두 처리하거나, 외부 호출에 타임아웃이 없거나, 테스트와 CI가 다른 명령을 쓰면 장애 때 동작을 예측하기 어렵다.

작동 방식

구조의 핵심은 폴더 트리가 아니라 책임 분리다. main은 얇게 두고 조립은 internal/app에 모으며, 공개 API가 아니면 internal에 둔다. main은 app.Run()만 부르고, internal/app이 설정 로딩, 의존성 조립, 프로세스 시작과 종료를 맡는다. main에서 조립까지 하면 테스트할 수 있는 진입점이 사라진다. pkg는 외부에 공개할 일이 생길 때만 연다. 너무 일찍 열면 API 호환성 부담이 생긴다. 처음에는 main.go 하나로 시작하고, 코드가 커지면 cmd와 internal로, 바이너리가 늘면 cmd/{api,worker,admin}으로 나눈다. 처음부터 계층을 많이 만들기보다, 경계가 생길 때 나누는 편이 유지보수에 유리하다. 경로만 도메인과 인프라로 나눠 놓고 책임은 섞어 두는 실수가 흔하다.

HTTP 서버는 응답이 나오느냐보다, 장애 때에도 예측 가능하게 멈추느냐로 견고해진다. 미들웨어는 Recover → RequestID → Logger → CORS → Auth → Handler 순서로 둔다. 순서가 깨지면 추적할 수 없는 로그, 놓친 패닉, 기록되지 않은 인증 실패가 생긴다. 핸들러에서 원천 에러를 직접 나누지 않고 도메인 코드로 매핑한다. 예를 들어 CodeNotFound는 404, CodeValidation은 400, 그 외는 500이다. 규칙이 있으면 에러 포맷과 모니터링 지표가 안정된다. 종료할 때는 새 요청을 막고, 진행 중인 요청에 제한 시간을 주며, 커넥션과 워커를 정리한 뒤 빠져나온다. 종료 신호는 signal.NotifyContext로 받고, 컴포넌트가 여럿이면 run.Group 패턴으로 종료 순서를 한곳에서 관리한다. readiness와 liveness를 나누고, 요청 타임아웃 기본값을 명시하며, 패닉에도 표준 에러 응답을 내고, access log에는 request id를 남긴다.

context.Context는 요청 범위 값, 타임아웃과 데드라인, 취소 신호를 나른다. 함수 첫 인자로 받고 구조체 필드에 저장하지 않으며, context.Background()는 진입점에서만 쓴다. 상위 타임아웃이 하위를 감싸게 두고, 모든 저장소와 외부 호출은 받은 ctx를 그대로 넘겨 취소를 전파한다. 클라이언트가 연결을 끊었는데 하위 호출이 계속 돌면 자원만 낭비된다. 타임아웃은 예를 들어 HTTP 전체 30초, 유스케이스 10초, DB 3초, 외부 API 5초처럼 겹쳐 둔다. WithValue에는 request id, trace id, 인증 주체만 담고, DB 핸들이나 큰 객체, 옵션 묶음은 넣지 않는다. 타임아웃 없는 외부 HTTP 호출, 새 고루틴에서 parent context를 빠뜨리는 일, 라이브러리 안에서 임의로 Background()를 만드는 일이 흔한 실수다.

동시성은 가벼운 goroutine을 무한히 만들어도 된다는 뜻이 아니다. Java 스레드의 초기 스택은 약 1MB이고 OS가 스케줄링하지만, goroutine은 초기 스택이 약 2KB이고 런타임이 M:N으로 스케줄하며 스택은 최대 1GB까지 늘어난다. 생성 비용이 낮아 실용적 상한은 수천 개가 아니라 수십만 개 수준이다. 다만 초기 스택 2KB에 디스크립터 약 400바이트를 더하면 goroutine당 약 2.4KB이고, 10만 개면 최소 240MB다. 컨테이너 메모리가 512MB에서 2GB 사이면 OOM 위험이 있다. 요청마다 goroutine을 만들고 외부 API가 늦어 대기가 쌓이면 제한을 넘어 강제 종료된다. 스레드 풀은 Worker Pool과 채널로, CompletableFuture는 errgroup으로, synchronized는 sync.Mutex로, BlockingQueue는 채널로 대응한다. CompletableFuture.allOf는 모두 끝나기를 기다리지만, errgroup은 첫 에러에서 나머지를 Context로 취소할 수 있다. 버퍼 없는 채널은 핸드셰이크에, 버퍼 있는 채널은 백프레셔와 비동기 전달에 쓰고, 채널은 만든 쪽(Producer)이 close한다. 공유 상태 보호에는 Mutex, 작업 분배와 이벤트에는 채널을 고른다. 경쟁 상태는 표준 -race 플래그로 잡고, 테스트 환경에서는 CI에 넣는 편이 안전하다. 패턴과 코드는 4편 동시성에 있다.

DB 연동의 핵심은 ORM 선택이 아니라 트랜잭션 경계 통제다. Spring의 @Transactional과 달리 Go에서는 경계를 코드에 드러내야 한다. WithTx 래퍼 한곳에서 성공 시 커밋, 에러 시 롤백을 보장하고, Repository는 트랜잭션을 만들지 않은 채 호출자가 준 ctx에서 핸들을 얻어 실행한다. 유스케이스 밖에 경계를 흩뿌리거나, Repository가 임의로 트랜잭션을 시작하거나, 긴 트랜잭션에 외부 API 호출을 넣지 않는다. 커넥션 풀은 MaxOpenConns를 DB 여유와 동시성에 맞춰 제한하고, MaxIdleConns는 그 30~50%, ConnMaxLifetime은 LB나 방화벽 타임아웃보다 짧게 두고 시작해 지표를 보며 맞춘다.

외부 호출은 Rate Limit → Circuit Breaker → Retry → Timeout 순서로 감싼다. 맨 바깥에서 과부하를 막고, 열린 회로가 불필요한 재시도를 차단하며, 재시도 여부를 타임아웃보다 먼저 정하고, 가장 안에서 개별 요청이 무한히 기다리지 않게 한다. Timeout은 모든 외부 호출에 필수다. 자세한 조합은 6편 외부 통신에 있다.

flowchart LR
    REQ[Request] --> RL[Rate Limit]
    RL --> CB[Circuit Breaker]
    CB --> RETRY[Retry]
    RETRY --> TIMEOUT[Timeout]
    TIMEOUT --> CLIENT[HTTP Client]

테스트는 도구보다 계층 분리가 먼저다. 유닛 테스트는 DB와 네트워크 없이 메모리에서 빠르게, 결정적으로 입출력 계약을 검증한다. 통합 테스트는 실제 인프라를 붙여 SQL, 인덱스, 트랜잭션 계약을 확인하고, 데이터는 케이스마다 독립적으로 둔다. mock은 gomock이나 손으로 짠 fake, 통합은 testcontainers-go, BDD가 필요하면 ginkgo와 gomega를 쓴다. PR에는 유닛과 핵심 통합만, main이나 nightly에는 전체 통합을 돌린다. 라벨로 나눠 실행하는 예는 ginkgo -r --label-filter='integration'이다. PR 단계 테스트는 10분 안에 끝나게 유지하고, 신규 기능에는 유닛과 통합 테스트를 하나씩은 둔다. mock을 과하게 써서 구현에 묶이거나, 통합 테스트가 전역 상태를 공유해 순서에 의존하거나, flaky 테스트를 무시하고 재시도만 늘리지 않는다. flaky가 나오면 바로 격리하고 원인을 제거한다.

관측성은 로그, 메트릭, 트레이스, 프로파일로 나눈다. 로그는 zap에서 Loki로 보내 디버깅과 감사에 쓰고, 메트릭은 Prometheus에서 Grafana로 보내 알림에 쓰며, 트레이스는 OpenTelemetry에서 Tempo로 보내 병목을 보고, 프로파일은 pprof로 성능을 본다. 상세한 대시보드와 알림 예는 8편 관측성에 있다.

Makefile의 본질은 자동화가 아니라 표준화다. 명령이 늘수록 팀마다 실행 방식이 달라지고 로컬과 CI 결과가 어긋난다. build, test, lint, generate, clean을 두고 개발자와 CI가 같은 명령을 쓰게 한다. test 타깃은 go test -race -cover ./...이고, 타깃은 .PHONY로 선언한다. 모노레포에서는 build-api, build-worker처럼 서비스별 타깃과 변경된 서비스만 빌드하는 타깃을 두고, help 타깃으로 문서를 대신한다. 환경별 분기를 과하게 넣거나 로컬에서만 되는 명령을 넣지 않는다.

외부 통신 패턴은 역할이 겹치지 않게 조합한다.

패턴목적적용
Timeout무한 대기 방지모든 외부 호출에 필수
Retry일시적 실패 복구5xx, 408, 네트워크 오류. 429는 기다린 뒤 재시도. 400, 401, 403, 404는 재시도하지 않음

테스트와 관측 계층도 역할을 섞지 않는다. 유닛은 빠른 피드백, 통합은 계약 검증이다. 로그 레벨은 프로덕션에서 DEBUG를 끄고, INFO와 WARN은 남기며, ERROR는 알림과 붙인다. 로거는 프로토타입에서 ReplaceGlobals로 빠르게 쓸 수 있지만, 정식 프로젝트에서는 Wire로 주입하는 편이 테스트하기 쉽다.

Timeout을 계층으로 나누는 출발점은 연결 5초, TLS 핸드셰이크 5초, 응답 헤더 10초, 전체 요청 30초다. 재시도는 100ms에서 시작해 200ms, 400ms, 800ms로 늘리고 지터를 섞는다. 지터가 없으면 동시에 실패한 클라이언트가 같이 재시도해 Thundering Herd가 난다. Circuit Breaker는 sony/gobreaker, Retry는 직접 구현하거나 avast/retry-go, Rate Limiting은 golang.org/x/time/rate, 통합은 failsafe-go를 쓸 수 있다.

실제 적용

외부 통신을 Timeout만 넣고 배포하면, 바깥 장애 때 요청이 쌓인다. 여기에 Retry만 더하면 재시도 폭풍이 나고, Circuit Breaker를 더해야 장애가 격리되며, 마지막에 Rate Limiting을 더해야 안정된다.

관측 메트릭은 RED(요청 수, 에러율, 응답 시간 분포)와 USE(CPU·메모리 사용률, goroutine 수로 보는 포화, 커넥션 실패 같은 리소스 에러)를 함께 본다. 대시보드는 Overview, HTTP, Database, External APIs 순으로 두고, 알림 예는 에러율 5% 초과 5분이 Critical(Slack과 PagerDuty), P99 1초 초과 5분이 Warning(Slack), 파드 재시작 1시간에 3회 초과가 Critical(Slack)이다. 의존성 에러율이 50%를 넘거나, DB 커넥션 풀 사용률이 90%를 넘거나, goroutine 수가 급증하면 단일 장애 지점을 의심한다. pprof는 CPU, Heap, Goroutine, Block 프로파일을 :6060에서 열고, 엔드포인트는 내부망이나 VPN에서만 연다.

  • Resilient한 외부 통신
