LLM 지식베이스는 에이전트가 다음 질문에서도 다시 쓸 수 있도록 근거와 현재 이해를 쌓아 두는 저장소다. 잘 만든 지식베이스는 가장 엄밀한 구조가 아니라, 싸게 기록하고 필요할 때 정확히 찾아내며 틀렸을 때 쉽게 고칠 수 있는 구조다. Recall-First Wiki

왜 필요한가

RAG는 질의와 관련된 자료를 context로 가져오는 검색 계층이다. 필요한 문서를 찾는 데는 쓸모 있지만, 어떤 자료가 지금 유효한지, 서로 충돌하는 두 문서를 어떻게 읽을지, 새 근거가 들어왔을 때 기존 설명을 어떻게 고칠지는 알려 주지 않는다. 문서를 모두 chunk로 나눠 벡터 DB에 넣으면 오래된 자료와 최신 자료가 함께 나오고, 좋은 답을 얻어도 다음 질문에서는 처음부터 다시 추론한다. 그래서 검색과 따로, 유지보수되는 지식 계층이 필요하다. Recall-First Wiki

그렇다고 그 계층을 엄밀하게 만들수록 좋아지지는 않는다. page type, trust, lifecycle 같은 상태를 잘게 나눈 초기 설계를 실제 질의로 점검해 보니 57개 페이지 중 기본 검색이 볼 수 있던 것은 15개뿐이었고, 업무형 질의 13개 중 8개가 필요한 지식을 찾지 못했다. 한 번 기록하기 전에 읽어야 하는 계약과 workflow가 약 8천 token이었고, 거버넌스 문서가 지식 문서 크기의 약 39%에 달했다. 잘게 나눈 trust와 lifecycle 값은 검색에도 답변에도 실제로 쓰이지 않았다. 파일은 많았지만 회수는 약했다. Recall-First Wiki

작동 방식

경계는 세 개만 둔다

영역담는 것규칙
raw/문서, 대화, 코드 분석 같은 원본 근거덮어쓰지 않는다. 고칠 일이 생기면 새 날짜의 근거를 더한다.
wiki/현재 이해와 결정새 페이지보다 기존 페이지를 먼저 고친다.
inbox/아직 확인하지 않은 메모와 수집 결과결론을 오래 두지 않는다.

검색된다는 이유만으로 수집 자료나 생성된 답을 지식으로 보지 않는다. Recall-First Wiki

절차도 셋이다: Recall, Capture, Compile

  • Recall: 전체 index나 ranked search로 후보를 찾고 관련 페이지를 읽는다. 중요한 주장이면 sources:를 따라 원문까지 내려가 확인하고, 사용한 지식 경로를 남긴다.
  • Capture: 새 문서, 대화, 직접 진술에 날짜와 출처를 붙여 raw/에 저장한다. 이 단계에서는 분류나 요약을 완벽하게 하지 않아도 된다. credential, token, private key 같은 비밀은 넣지 않는다.
  • Compile: 기존 페이지를 먼저 고치고, 반복해서 찾을 주제일 때만 새 페이지를 만든다. 불확실성은 enum 대신 (unverified), (superseded by X, 2026-07-16) 같은 표시로 본문에 바로 적는다. sources:로 근거를 잇고 index와 lint를 갱신한다.

claim ledger나 승격 queue를 따로 돌리지 않고, 사람이 읽는 문장 안에 인식 상태를 적는 방식이다. Recall-First Wiki

메타데이터는 라우팅에 쓰이는 만큼만

frontmatter는 title, summary, sources, updated 정도면 대부분의 라우팅과 검증이 된다. 그중 핵심은 summary다. 다음 에이전트가 본문을 열지 말지 한 줄로 판단할 수 있어야 한다. 민감정보 등급도 셋으로 줄였다. open은 일반 기술 지식, work는 업무에는 검색되지만 외부 결과물에는 나오면 안 되는 정보, private은 개인 요청에서 명시적으로 허용할 때만 검색하는 정보다. private은 기본 검색에서 빼고, work는 공개 문서를 쓸 때 막으며, secret은 등급과 상관없이 저장하지 않는다. Recall-First Wiki

lint는 필수 frontmatter, 깨진 링크, index 최신성, 금지된 secret 패턴처럼 기계로 판단할 수 있는 일만 좁고 결정적으로 맡는다. 요약이 원문을 정확히 반영하는지, 오래된 판단이 갱신됐는지 같은 의미 판단은 본문과 원문 검토로 다룬다. Recall-First Wiki

검색은 완전한 index부터

이 규모에서는 벡터 DB보다 다음이 먼저 효과를 냈다. 모든 페이지를 담은 자동 생성 index, 열지 말지 판단할 한 줄 summary, lexical ranked search, 상위 결과 본문을 묶어 주는 context 명령, 검색 실패를 드러내는 실제 질의 세트다. index가 빠져 있고 summary가 부정확하면 임베딩을 더해도 corpus 자체의 문제는 그대로 남는다. hybrid 검색은 lexical 검색이 실제 평가에서 반복해서 실패할 때 들인다. Recall-First Wiki

기록과 검색을 나눠 잰 실험

Personal LLM Memory 실험은 실패를 세 갈래로 나눠 쟀다. 원문이 올바른 메모리 전이로 컴파일됐는지(K), 고정된 컴파일 결과를 검색이 제대로 썼는지(Q), 둘을 묶은 전체 파이프라인이 쓸 만한 답의 전제를 만들었는지(K × Q)다. 질의 팩과 컴파일 팩은 각각 100건으로, 개발용 20건과 held-out 80건이다. 아키텍처 평가

  • 검색만 볼 때: lexical(A0) 70.85%, BM25F(B1) 74.28%에서 graph/source closure(C1)로 가며 86.73%가 됐다. 통계적으로 뒷받침된 큰 개선은 이 B1 → C1(+12.45포인트) 하나였다. policy/trust rerank(D1), hybrid RRF(E1), adaptive router(F1)는 모두 87.98%, 80건 중 71건으로 같았다. 형식상 우승은 동점 규칙에 따라 F1이었지만, 운영 기본값은 D1로 정했다. D1은 F1보다 p95 지연이 28.2% 낮고 dense 모델에 기대지 않는다. 대신 median context가 3.7% 더 길다. 아키텍처 평가
  • 둘을 묶었을 때: K3 policy incremental 컴파일러와 Q2 policy graph 검색 조합이 held-out 80건 중 31건(38.75%)으로 가장 앞섰지만, 모든 조합이 배포 hard gate를 하나 이상 넘지 못해 배포할 우승 조합은 없었다. K3 × Q2의 실패 49건 중 47건이 컴파일에서, 2건이 검색에서 났다. Q2를 고정하면 컴파일러 단계를 올릴 때마다 유의한 개선이 있었고, K3를 고정하면 Q0 → Q1, Q1 → Q2가 각각 5포인트씩 올랐지만 다중 비교 보정 뒤에는 유의하지 않았다. 아키텍처 평가
  • 일관성: K3는 test-only metamorphic 비교 320건 중 76건만 통과했다. 같은 의미의 계획(equivalent-plan)은 160건 중 40건, 최소 변경(minimal-delta)은 128건 중 4건이었다. 이 결과 때문에 K3는 프로덕션으로 올리지 않았다. 아키텍처 평가

그래서 운영 구조는 이렇게 남았다. 쓰기는 결정적 ingest와 관리되는 컴파일 흐름으로 하고, wiki/의 metadata-v2 Markdown만 영속 메모리로 둔다. 읽기 전에 정책 범위를 먼저 적용하고, D1(BM25F, trust/time rerank, graph/source closure, bounded packing)으로 읽는다. trust 승격, 모순 해소, 민감한 라우팅, 삭제 확인은 사람이 검토한다. 아키텍처 평가

다음 목표는 쓰기 경로부터다. Phase A에서는 근거를 보존하는 typed memory transition compiler를 만든다. ADD, CONFIRM, CONTEST, SUPERSEDE, RETRACT, FORGET, NOOP 전이를 명시하고, 새로 고정한 100개 시퀀스에서 전이·최종 상태 정확도 90% 이상, action precision과 recall 95% 이상을 넘겨야 승격한다. 그동안 D1 검색은 고정해서 개선 효과가 쓰기 경로에서 왔는지 가린다. fingerprint 기반 영속 sparse/graph cache(Phase B)는 Phase A를 통과한 뒤에만 붙인다. 다음 목표 연구

선택지와 트레이드오프

  • 엄밀한 거버넌스와 기록 비용: 근거와 해석을 나누고 민감정보를 통제하며 지식 상태를 드러내는 설계는 논리적으로 맞았다. 하지만 에이전트가 읽어야 할 정책만 늘고 정작 답에 필요한 지식은 context에 들어오지 않았다. Recall-First Wiki
  • source digest: 원문마다 digest를 만들면 짧은 원문까지 다시 요약해 중복이 늘고, 맥락이 잘리고, 검색 결과에 원문과 digest가 함께 떠 노이즈가 된다. 작고 읽기 쉬운 원문은 직접 인용하고, 크거나 복잡한 원문에만 digest를 만들며, digest를 1차 근거로 쓰지 않는다. Recall-First Wiki
  • dense 검색: 정확도가 같다면 지연이 낮고 dense 모델에 기대지 않는 D1을 골랐다. 다만 실험에 실제 dense 구현(Q3)이 없어 trigram 대리 구현으로 대신할 수 없었으므로, 이 결과가 dense 검색에 불리한 증거는 아니다. 아키텍처 평가
  • 측정의 한계: token 값은 tokenizer나 과금 기준이 아닌 추정치다. 50,000 단위 수치는 용량 시험이 아니라 선형 외삽일 뿐이다. 답변 품질, live MCP, dense 검색, 프로덕션 처리량은 이 평가로 증명되지 않았다. 아키텍처 평가

품질을 재는 기준

지식베이스는 저장량이 아니라 회수율, 원문까지의 추적 가능성, 갱신 비용으로 평가한다. 실제 질문에서 필요한 페이지가 상위에 나오는지, 답에 쓴 주장을 원문까지 따라갈 수 있는지, 새 근거가 기존 페이지를 고치는지, 같은 개념이 여러 이름으로 흩어지지 않는지, 기록 한 번에 드는 절차와 token이 지나치지 않은지, private과 work 정보가 엉뚱한 결과물에 섞이지 않는지, 검색 실패를 발견하고 고칠 수 있는지를 본다. Recall-First Wiki
