MongoDB는 수평 확장을 샤딩으로, 노드 안의 저장을 WiredTiger 스토리지 엔진으로 처리하는 문서 DB다. 둘 다 기본값으로 시작할 수 있지만, 규모가 커지면 샤딩은 샤드 키가, WiredTiger는 캐시·체크포인트·저널 정책이 비용과 지연을 결정한다.

왜 필요한가

샤딩은 빨라지는 기능이 아니라 용량과 처리량의 한계를 넘기 위한 구조다. 단일 노드의 디스크나 메모리가 한계에 가까워질 때, 쓰기 처리량을 수직 확장으로 감당하지 못할 때, 특정 컬렉션이 계속 핫스팟을 만들 때 들인다. 한번 들이면 샤드 키가 장기 운영 비용을 좌우하므로, 초기 설계에서 쿼리 패턴과 키 분포를 함께 검증해야 한다.

WiredTiger는 구현 세부보다 병목이 어디서 생기는지를 알아야 하는 대상이다. 캐시, 체크포인트, 저널 설정이 서로 맞물려 지연과 내구성을 함께 정하기 때문이다.

작동 방식

샤딩 구성

  • mongos: 라우터. 클라이언트 요청을 알맞은 샤드로 보낸다.
  • shard replica set: 실제 데이터를 저장한다.
  • config server replica set: chunk와 메타데이터를 저장한다.

최소 구성은 데이터베이스에 샤딩을 켜고, 컬렉션과 샤드 키를 지정하는 두 단계다.

쿼리에 샤드 키가 들어 있으면 해당 샤드만 조회하는 targeted query가 되고, 없으면 모든 샤드를 도는 scatter-gather가 된다. 둘의 운영 비용 차이가 크기 때문에, 주요 API는 샤드 키를 쿼리에 넣도록 계약을 잡는다.

WiredTiger의 쓰기 경로

WiredTiger는 저널(WAL)에 먼저 기록하고, 메모리 캐시에 반영한 뒤, 체크포인트 때 디스크에 내린다. 이 순서 덕분에 장애 복구와 성능을 함께 잡는다. 문서 수준 동시성과 MVCC로 읽기와 쓰기가 서로 덜 막혀 읽기·쓰기가 섞인 워크로드에 유리하다.

선택지와 트레이드오프

샤드 키 전략

좋은 샤드 키는 카디널리티가 높고, 고르게 퍼지며, 실제 쿼리 패턴과 맞아야 한다. 세 조건을 동시에 채워야 한다.

전략장점단점맞는 경우
Hashed분산이 고르다범위 조회가 비효율적이다랜덤 조회 중심
Ranged범위 조회가 효율적이다시간축 핫스팟 위험이 있다시계열, 정렬 조회
Compound분산을 유연하게 설계할 수 있다설계와 운영이 복잡해진다복합 조건 조회

WiredTiger 튜닝

엔진 튜닝은 옵션 하나를 최적화하는 일이 아니라 캐시, 체크포인트, 저널 정책을 함께 맞추는 일이다.

  • 캐시 크기: 작으면 eviction 압력이 커져 지연이 튀고, 크면 시스템 전체 메모리가 압박받는다. 관측한 뒤 조정한다.
  • 내구성 설정: 체크포인트와 저널 내구성을 낮추면 TPS가 오르지만, 장애 때 잃는 범위가 커진다. SLO를 기준으로 정한다.
  • 압축: 저장 공간과 CPU를 맞바꾼다. 기본 압축에서 시작하고 I/O 병목이 심할 때만 다시 본다.

자주 하는 실수

  • createdAt 하나처럼 단조 증가하는 키를 샤드 키로 써서 쓰기가 한 샤드에 몰린다.
  • chunk 분할과 이동이 피크 시간과 겹쳐 지연이 급증한다.
  • 샤드 키를 나중에 바꾸기 어렵다는 제약을 늦게 알아 마이그레이션 비용이 커진다.

운영 점검 항목

  • sh.status()와 getShardDistribution()을 정기적으로 확인한다.
  • 밸런서 작업 시간대를 트래픽 저점으로 제한한다.
  • 샤드 키 후보는 실제 트래픽으로 리허설한 뒤 정한다.
  • 다중 샤드 트랜잭션 비율을 지켜본다.
  • serverStatus().wiredTiger를 정기적으로 수집하고, eviction 지표와 write latency를 함께 본다.
  • 체크포인트 스파이크가 나는 시간대를 파악하고, 대량 배치는 평시 트래픽과 떼어 놓는다.
