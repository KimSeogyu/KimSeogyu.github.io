여러 프로세스가 같은 작업을 시작할 때는 Redis 락으로 실행을 조율하고, 감사 이벤트를 나눠 처리할 때는 Redis Streams에 이벤트와 처리 상태를 남긴다. 실시간 연결이 여러 서버에 흩어져 있으면 Redis에서 세션 위치를 찾아 메시지를 보내고, 연결이 끊긴 동안 놓친 이벤트를 다시 전달할 수 있다.

왜 필요한가

Redis는 쓰기 쉬운 만큼 잘못 쓰기도 쉽다. 락을 잡은 프로세스가 멈춰도 락이 영원히 남아서는 안 되고, 락은 잡는 것보다 안전하게 푸는 것이 더 어렵다. 감사 이벤트를 읽은 워커가 처리 도중에 멈췄다면 다음에 다시 읽을 수 있도록 그 이벤트가 미처리 상태로 남아야 한다. 락에는 만료 시간이, 이벤트에는 처리 완료를 알리는 절차가 필요한 이유다.

작동 방식

락을 잡은 프로세스만 해제한다

SET key value NX PX ttl은 키가 없을 때만 고유 토큰(UUID)을 값으로 쓰고 만료 시간(TTL)을 설정한다. 해제할 때는 Lua 스크립트 안에서 저장된 토큰과 자신의 토큰을 비교해 일치할 때만 DEL을 실행한다. 그래야 이전 소유자가 뒤늦게 작업을 마쳐도 새 소유자의 락을 지우지 않는다. 작업이 TTL보다 길어질 수 있으면 갱신 방법을 정하고, 락 획득에 실패하면 백오프를 두고 재시도한다.

감사 이벤트는 처리에 성공한 뒤 ACK한다

생산자가 감사 이벤트를 스트림에 기록하면 소비자 그룹의 워커들이 나눠 읽는다. 워커는 새 이벤트를 >로 읽고, 자신이 읽었지만 아직 처리 완료를 알리지 않은 이벤트(pending)는 0으로 다시 읽는다. 핸들러가 성공한 뒤에만 ACK해야 처리 도중 멈춘 이벤트를 다시 시도할 수 있다.

전달 횟수(delivery count)가 재시도 한도를 넘으면 해당 이벤트를 별도 스트림(DLQ)에 격리한다. 운영할 때는 pending 개수와 재시도율, DLQ 유입량을 살피고 멈춘 소비자를 감지해 복구한다. 스트림 길이는 XTRIM으로 관리한다. 메시지 스키마 버전을 관리하고, 범위를 지정해 다시 처리하는(replay) 도구도 준비한다.

실시간 메시지는 세션이 있는 서버로 보낸다

보내는 서버는 Redis Hash에서 수신자의 서버 ID를 찾고 Pub/Sub로 해당 서버의 채널에 메시지를 발행한다. 받은 서버는 로컬 소켓으로 메시지를 넘긴다. 이벤트는 Streams에도 남겨 둔다. 클라이언트가 재연결하면서 마지막으로 받은 이벤트 ID를 보내면 그 뒤에 놓친 이벤트를 다시 전달한다. 트래픽 확장 설계

선택지와 트레이드오프

Redis 락은 배치 중복 실행이나 캐시 재생성 경합을 줄이는 데 적합하다. 엄격한 정합성까지 필요하지 않은 스케줄러의 리더 선출에도 쓸 수 있다. 락만으로 작업이 정확히 한 번 실행된다고 보장할 수 없으므로 실패 시 보상 방법을 함께 정한다. Redlock은 락의 가용성을 높이려는 방식이다. 원장처럼 강한 정합성이 필요한 작업은 DB 트랜잭션이나 합의 기반 락을 먼저 검토한다.

Streams는 빠른 큐가 아니라 상태가 있는 로그다. 이벤트를 적어도 한 번(at-least-once) 처리할 수 있도록 미처리 기록을 남긴다. 워커가 멈춰도 재처리할 수 있는 대신, 재시도 횟수와 쌓이는 이벤트 수를 관리해야 한다.

자주 하는 실수

  • 락에 TTL을 두지 않으면 소유자가 멈춘 뒤에도 락이 남는다.
  • 워커가 재시작할 때 >로 새 이벤트만 읽으면 이전에 읽은 이벤트가 pending 상태로 남는다.
  • 핸들러 실행 전에 ACK하면 처리에 실패한 이벤트가 pending 목록에서 빠진다.
