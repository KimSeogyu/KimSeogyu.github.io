PostgreSQL 성능 관리는 데이터의 모양에 맞는 인덱스를 고르고, 느린 쿼리는 추측하지 않고 실행 계획과 실행 통계로 진단하는 일이다. 스칼라 값에는 기본 인덱스인 B-Tree로 대부분 충분하지만, 대소 비교로 답할 수 없는 질문에는 GiST, GIN, BRIN 같은 인덱스가 필요하다.

왜 필요한가

B-Tree는 “왼쪽이 작고 오른쪽이 크다”는 순서 관계에 기대는 구조다. 그래서 등가 조건, 범위 조건, 정렬에는 강하지만 다음 같은 질문에는 답하지 못한다.

  • 서울역에서 반경 1km 안에 있는 카페는?
  • 이 문서에 ‘PostgreSQL’과 ‘index’가 모두 나오는가?
  • 이 시간대와 겹치는 예약이 있는가?

이런 질문은 단순한 대소 비교가 아니라 다른 차원의 비교가 필요하다. 인덱스 Deep Dive

반대로 인덱스를 잘 골라도 쿼리를 감으로 고치면 효과를 확인할 수 없다. 튜닝은 마법 옵션이 아니라 측정, 가설, 검증을 반복하는 과정이다.

작동 방식

인덱스 유형

유형맞는 데이터대표 연산자특징
B-Tree숫자, 문자열 같은 스칼라 값=, <, >, BETWEEN, ORDER BY기본값, 범용
Hash등가 비교만 필요할 때=범위 검색 불가
GiST공간, 범위, 전문 검색@>, <@, &&, <->확장할 수 있는 틀
GIN배열, JSONB, 전문 검색@>, ?, @@역인덱스, 읽기에 유리
BRIN순서대로 쌓이는 대용량 데이터범위 기반아주 작음

B-Tree는 노드 하나에 정렬된 키를 여러 개 담는 균형 트리다. 루트에서 대소 비교로 내려가 O(log n)에 찾고, 삽입 때 페이지가 넘치면 나누고, 삭제 때 모자라면 합친다.

GiST: 조건식으로 나누는 트리

GiST(Generalized Search Tree)는 인덱스 하나가 아니라 새 인덱스 유형을 만드는 틀이다. 새 인덱스를 바닥부터 만들려면 락, WAL, 버퍼 관리를 직접 다뤄야 하지만, GiST가 이 부분을 맡아 주므로 도메인 로직만 구현하면 된다.

B-Tree가 값의 순서로 자식을 찾는다면, GiST는 노드마다 조건식(predicate)을 둔다. 리프는 “이 행은 조건 P를 만족한다”, 내부 노드는 “내 자식은 모두 조건 P를 만족한다”는 뜻이고, 내부 노드의 조건은 자식을 모두 포함하는 가장 작은 범위다. GiST 위에 만든 R-Tree는 이 범위를 최소 사각형(MBR)으로 표현한다. 점도 크기가 0인 사각형으로 저장해서 점, 선, 다각형을 같은 구조로 다룬다.

검색은 루트에서 깊이 우선으로 내려가며 consistency 함수로 “이 노드를 볼 필요가 있는가”를 판단한다. 반경 검색이라면 원과 겹치지 않는 MBR의 하위 트리는 건너뛰고, 겹치는 쪽만 내려간다. 조건에 맞는 노드가 여럿일 수 있어 B-Tree와 달리 여러 경로를 탐색한다.

삽입은 부모 MBR이 가장 적게 커지는 위치를 고른다. 삭제할 때는 리프에서 데이터만 빠지고 부모 MBR은 줄어들지 않는다. 그래서 변경이 잦은 테이블에서는 인덱스 효율이 떨어지고, 정기적으로 REINDEX나 VACUUM FULL이 필요할 수 있다.

튜닝 절차

  1. pg_stat_statements로 느린 쿼리를 모은다.
  2. EXPLAIN (ANALYZE, BUFFERS)로 계획과 실행 통계를 본다.
  3. 병목이 스캔, 조인, 정렬, 락 중 어디인지 가른다.
  4. 인덱스, 쿼리, 스키마 중 가장 작은 변경부터 적용한다.
  5. 다시 잰다.

자주 만나는 병목은 네 가지다.

병목원인대응
Seq Scan 과다필터 컬럼 인덱스가 없거나 통계가 부정확인덱스 추가, ANALYZE, 조건식 단순화
잘못된 복합 인덱스 순서범위 조건 컬럼이 앞에 있음등호 조건 컬럼을 앞, 범위 조건 컬럼을 뒤에 둠
정렬·해시 spillwork_mem이 작거나 불필요한 ORDER BY설정과 쿼리 점검
인덱스 과다읽기만 보고 인덱스를 계속 추가쓰지 않는 인덱스 정리

선택지와 트레이드오프

  • 기본은 B-Tree다. 특별한 이유가 없으면 다른 인덱스를 쓰지 않는다. 공간 데이터와 범위 겹침은 GiST, 포함 관계와 전문 검색은 GIN, 순차적인 대용량 데이터는 BRIN을 쓴다.
  • GiST와 B-Tree: B-Tree는 정렬과 유니크 제약을 자연스럽게 지원한다. GiST는 정렬을 보장하지 않지만 거리 정렬은 지원하고, 유니크 제약 대신 그것을 일반화한 배타 제약(exclusion constraint)을 쓴다.
  • GiST와 GIN: 전문 검색에서는 대개 GIN이 더 정밀하고 빠르다. GiST는 시그니처로 동작해 false positive가 생길 수 있다. 대신 삽입은 GiST가 더 빠를 수 있어 쓰기가 많은 워크로드에서 고려할 만하다. k-NN 검색은 GiST만 지원한다.
  • 인덱스는 공짜가 아니다. 읽기는 빨라져도 쓰기와 유지 비용이 늘어난다.

예시

  • k-NN 검색: GiST 공간 인덱스를 만들고 ORDER BY geom <-> ST_MakePoint(127.0, 37.5) LIMIT 10처럼 <-> 연산자로 가까운 순서대로 가져온다. 인덱스 Deep Dive
  • 예약 중복 막기: tsrange 컬럼에 GiST 인덱스를 두고 &&로 겹치는 예약을 찾는다. btree_gist 확장을 켜고 EXCLUDE USING GIST (room_id WITH =, time_range WITH &&) 제약을 걸면, 같은 방에 겹치는 예약을 넣는 순간 거부된다. 인덱스 Deep Dive
  • 인덱스 내부 보기: B-Tree는 pageinspect 확장의 bt_metap, bt_page_items로, GiST는 gevel 확장의 gist_stat, gist_tree로 들여다본다. 인덱스 Deep Dive
  • PostGIS: GeoJSON 호환을 위해 SRID를 보통 4326으로 통일하고 GIST 인덱스를 둔다. 공간 조회 성능은 거의 항상 이 인덱스 유무로 갈린다. 거리 계산은 geography로 캐스팅해야 실수가 적고, 잘못된 도형은 ST_MakeValid로 고치되 원본을 보존할 컬럼을 둔다. GeoJSON 출력은 소수 6자리면 대부분의 웹 지도에 충분하다. PostGIS

운영 체크리스트

  1. 배포 전에 핵심 쿼리의 계획을 비교한다.
  2. 느린 쿼리 상위 10개를 계속 추적한다.
  3. 쓰지 않는 인덱스를 정기적으로 지운다.
  4. 대량 데이터 변경 뒤에는 ANALYZE를 돌린다.
  5. 변경이 잦은 테이블의 GiST 인덱스는 정기적으로 재구성한다.

단일 쿼리를 최적화하기보다 반복할 수 있는 튜닝 절차를 먼저 만든다.
