트랜잭션과 격리수준

2026년 11월 19일

  • Database
  • Transaction
  • PostgreSQL
  • MySQL

트랜잭션은 동시에 들어오는 쓰기 속에서 데이터가 규칙을 지키게 하는 DB의 기본 장치다. ACID는 기본값으로 저절로 지켜지지 않는다. 트랜잭션을 어디서 시작하고 끝낼지, 어떤 이상현상을 허용할지, 같은 키에 쓰기가 몰릴 때 어떻게 처리할지를 도메인에 맞게 정해야 한다.

왜 필요한가

ACID를 깨는 것은 대개 애플리케이션이다. 경계를 너무 넓게 잡아 락 경합을 키우고, 격리수준을 모른 채 기본값을 쓰다 팬텀 리드나 갱신 손실을 겪으며, 커밋 전에 메시지를 발행하거나 캐시를 바꾸고, 복구 리허설 없이 백업만 믿는다. ACID는 이론이 아니라 운영 계약이라, 트랜잭션 경계, 격리수준, 장애 복구 시나리오를 코드와 문서로 함께 관리해야 지켜진다.

네 가지 특성은 이것이다. Atomicity는 전부 성공하거나 전부 실패하는 것이고, Consistency는 전후로 제약조건과 데이터 규칙이 유지되는 것이며, Isolation은 동시에 실행되는 트랜잭션 사이 간섭이 제어되는 것이고, Durability는 커밋된 결과가 장애 이후에도 남는 것이다.

작동 방식

트랜잭션 안에서는 DB 변경 외의 일을 줄인다. 커밋 뒤 이벤트는 outbox 같은 패턴으로 맞추고, 교착상태 재시도 정책(횟수와 백오프)은 명시해 둔다. 백업 복구를 리허설하지 않으면 durability를 만족했다고 보기 어렵다.

격리수준의 정답은 없다. 허용할 수 있는 이상현상과 필요한 처리량 사이에서 고른다. 대부분의 OLTP는 READ COMMITTED로 충분하다. 같은 트랜잭션 안에서 재조회 일관성이 필요하면 REPEATABLE READ를 쓰고, 이는 MySQL 기본값이기도 하다. 정합성이 최우선이고 처리량을 희생할 수 있는 좁은 구간만 SERIALIZABLE로 올린다. READ UNCOMMITTED는 일반 서비스에 권하지 않는다. 전역 기본값은 READ COMMITTED로 두거나 MySQL 기본 전략을 유지하고, 민감한 트랜잭션만 상위 격리수준으로 승격한다. 바꾸기 전에 deadlock과 지연을 리허설하고, 버전 컬럼을 쓰는 낙관적 잠금을 함께 검토한다.

고를 때는 더티 리드를 절대 허용할 수 없는지, 같은 트랜잭션 안에서 재조회 결과가 바뀌면 문제인지, 팬텀 리드를 애플리케이션이 처리할 수 있는지, 락 경합 지연을 감당할 수 있는지를 묻는다. 격리수준은 DB 파라미터가 아니라 비즈니스 정책이다.

DB 하나로 끝나지 않으면 일관성 모델을 고른다. 강한 일관성의 2PC/XA는 운영 복잡도와 지연을 늘리고, 보상 트랜잭션 기반 Saga는 최종 일관성을 받아들인다. 기준은 도메인의 실패 허용치다.

“없으면 넣고 있으면 고친다”는 애플리케이션에서 분기하지 않고 DB에 맡긴다. SELECT 뒤에 INSERT나 UPDATE를 나누면 왕복이 늘고, 그 사이에 다른 트랜잭션이 끼어들 수 있으며, 애플리케이션 분기도 복잡해진다. Upsert(ON CONFLICT, ON DUPLICATE KEY UPDATE)는 한 문장에서 원자적으로 처리해 경합 구간을 줄인다. 대량 인덱싱이나 동기화에서는 사실상 기본 선택이다.

PostgreSQL은 INSERT ... ON CONFLICT (id) DO UPDATE SET col = EXCLUDED.col이고, MySQL은 INSERT ... ON DUPLICATE KEY UPDATE col = VALUES(col)이다. 여러 행을 한 문장에 넣는 배치 Upsert도 같은 꼴이다. 유니크 키가 분명해야 하고, 정말 필요한 컬럼만 갱신하며, 같은 입력이면 같은 결과가 나오게 하고, 배치 크기가 락 경합을 키우지 않게 한다.

선택지와 트레이드오프

격리수준쓰는 때주의
READ COMMITTED대부분의 OLTP 기본 선택같은 트랜잭션 안 재조회가 달라질 수 있음
REPEATABLE READ재조회 일관성이 필요할 때. MySQL 기본값락 경합과 지연이 늘 수 있음
SERIALIZABLE정합성이 최우선인 좁은 구간처리량을 희생할 수 있어야 함
READ UNCOMMITTED일반 서비스에는 비권장더티 리드를 허용함
일관성 모델이득대가
2PC/XA강한 일관성운영 복잡도와 지연 증가
Saga서비스별 실패를 보상 트랜잭션으로 처리최종 일관성을 받아들여야 함
SELECT 후 분기구현이 단순해 보임왕복 증가, 중간에 다른 트랜잭션 개입
Upsert원자성과 경합 감소유니크 키, 배치 크기, 갱신 컬럼 설계가 성능을 좌우

성능은 문법이 아니라 유니크 키 설계, 배치 전략, 갱신 컬럼 최소화로 결정된다.

실제 적용

큰 TEXT나 BLOB 컬럼까지 매번 갱신하면 쓰기 비용이 급증한다. 트리거나 CDC가 UPDATE 이벤트 폭증으로 막히기도 하고, 애플리케이션 타임스탬프와 DB 타임스탬프를 섞으면 정합성이 깨진다. 배치 크기를 먼저 고정해 기준선을 잡고, EXPLAIN (ANALYZE, BUFFERS)로 실제 경로를 확인한다. 실패 재시도는 같은 입력이면 같은 결과가 되게 설계한다.
