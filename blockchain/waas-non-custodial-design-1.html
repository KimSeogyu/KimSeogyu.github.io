이 글은 두 편으로 나뉩니다. 이어지는 실행 계획과 시나리오는 WaaS Non-Custodial 개선 설계 (2)에 있습니다.

0. 결론과 제출물

본 답안은 Track A — WaaS Non-Custodial 설계에 집중한다. Track B의 ERC-4337 역할 분리와 Track D의 EIP-8141 대응은 핵심 설계가 장기적으로 깨지지 않도록 연결점만 짧게 다룬다.

현재 WaaS가 custodial로 판정되는 이유는 서버가 K_D, envelope 같은 서버 보관 재료를 통해 유효한 wallet approval 또는 그에 준하는 서명 능력을 만들 수 있다는 점이다.

목표 구조는 Passkey-first WaaS다. 이 설계에서는 PAKE를 wallet control에 사용하지 않는다. password-like 입력은 복구 백업을 암호화하기 위한 high-entropy recovery passphrase뿐이다.

1. 문제 재진술과 설계 원칙

1.1 현재 구조의 custody 문제

판정 축현재 구조의 문제개선 방향
서명 통제권서버가 K_D 또는 동등한 재료로 유효한 tx approval을 만들 수 있음Smart Account가 인정하는 승인 근거를 사용자 기기 Passkey proof 또는 사전 등록된 온체인 policy로 제한
키 재현 가능성서버 재료와 저엔트로피 패스워드 공간이 결합되면 서명 능력 복구 위험이 있음PAKE-derived wallet key 경로 제거. 복구 백업 암호화에는 별도의 high-entropy recovery passphrase만 사용
키 저장·지속성유저가 서버와 독립적으로 지갑 접근 권한을 증명하기 어려움독립 challenge signing, EIP-1271 검증, registered public key 조회로 증명

현재 구조에서는 아래 조합이 한 운영 경계 안에 모이면 유저 서명을 재현하거나 그에 준하는 실행 권한을 만들 수 있다.

권한 조합가능한 일위험도
WaaS DB 접근 + K_D 접근 + tx worker 접근유저 개입 없이 UserOperation 또는 커스텀 실행 경로 생성높음
서버 인증 재료 + per-user envelope + 저엔트로피 패스워드 공간K_S 또는 동등한 서명 능력 복구 시도높음
Bundler / Paymaster / Signer가 같은 운영 경계대납 정책, 제출, 서명 권한이 함께 오남용될 수 있음중간~높음
Tenant backend + WaaS API 권한 + preview 불일치유저에게 보인 내용과 실제 action이 달라질 수 있음중간

이 설계의 목표는 위 조합을 끊는 것이다.

1.2 설계 원칙

원칙설명
Account Session ≠ Wallet Execution Authority ≠ Recovery Authority같은 Passkey ceremony를 계정 세션 생성과 wallet approval에 함께 쓸 수 있다. 다만 계정 세션이 곧 wallet 실행 권한이 되면 안 된다.
Wallet approval은 사용자 기기에서만 생성Passkey private key는 사용자 기기 밖으로 나가지 않는다.
WaaS는 approval 생성자가 아님WaaS는 Action 생성, 검토, 수수료 처리, 제출 상태 관리를 오케스트레이션하지만 사용자 대신 approval을 만들지 않는다.
Smart Account가 최종 검증자서버의 “승인됨” 상태를 믿지 않고 Passkey proof, recovery proof, policy를 직접 검증한다.
Action은 canonical object유저가 본 preview와 서명 대상 hash를 강하게 묶는다.
반복 실행은 온체인 policy 기반서버가 signed action을 보관해 임의로 재실행하지 않는다.
PAKE는 wallet control에서 제외PAKE가 남더라도 인증 보조 수단일 뿐, wallet approval이나 recovery authority로 쓰지 않는다.

1.3 권한 의미 분리

나누어야 하는 것은 credential의 종류가 아니라 권한의 의미다.

권한 문맥책임허용 수단금지 사항
Account Session사용자가 누구인지 확인하고 flow 시작Passkey ceremony, 앱 내부 세션세션만으로 Action 실행, owner 변경, recovery policy 변경
Wallet Execution Authority특정 Action, owner 변경, policy 등록 승인등록된 Passkey의 action-bound P-256 proof, Smart Account verifieraccount-session assertion 재사용, 서버 대리 서명, password-derived signing
Recovery Authority승인 수단 분실 시 새 approval method 등록/교체recovery proof, 기존 기기 승인, 선택적 guardian평상시 결제 승인, 계정 세션만으로 owner 교체
Automation Scope정기결제·반복 실행온체인 policy module, allowedExecutor, cap, interval, expiry, nonce범용 서버 서명, owner mutation

사용자 경험에서는 “Passkey로 계정 세션을 만들고 곧바로 wallet approval을 진행하는 흐름”처럼 보일 수 있다. 하지만 Smart Account 관점에서는 account session과 wallet approval이 분리되어야 한다. Wallet approval은 wallet, chainId, actionHash, nonce, expiry, purpose에 묶인 canonical challenge에 대한 proof여야 한다.

2. 목표 구조와 컴포넌트 경계

핵심은 Wallet Directory의 성격이다. Backend가 tenantUserRef → wallet address를 조회할 수는 있지만, 이 정보는 account discovery와 flow routing을 위한 directory일 뿐이다. 실제 owner approval, recovery authority, 자동결제 policy 실행 가능 여부는 Smart Account가 검증한다.

2.2 SDK Flow Runtime / WaaS Flow Backend

구조상 flow는 두 층으로 나뉜다.

즉, SDK도 flow를 갖지만 실행 권한의 판단 주체는 아니다. WaaS도 실행을 오케스트레이션하지만 사용자 approval을 생성하지 않는다. 최종 권한 검증은 Smart Account가 직접 수행한다.

2.3 App-facing API

Tenant App이 Wallet Directory, Action Builder, Review, Tx Compiler, Submitter 같은 내부 모듈을 직접 호출하면 안 된다. App-facing API는 SDK가 사용하는 고수준 flow API로 제한한다.

API호출자의미금지되는 해석
POST /flowsTenant App / SDK지갑 생성, 기기 추가, 복구, 결제, 자동결제 등록 같은 고수준 flow 시작내부 Action/Review/Compiler를 App이 직접 제어하는 API가 아님
POST /flows/{flowId}/approvalsTenant App / SDK사용자 기기에서 생성된 Passkey approval proof 또는 recovery proof 제출서버가 대신 approval을 만들어주는 API가 아님
GET /flows/{flowId}Tenant App / SDKpending approval, submitted, confirmed, failed 등 상태 조회wallet owner 여부를 서버가 판정한다는 뜻이 아님

3. Action, 실행 포맷, 자동결제

3.1 Canonical Action

사용자가 승인하는 의미 단위와 실제 실행 포맷을 분리한다.

previewHash가 중요하다. 유저가 본 UI 문구, 금액, 대상, 수수료 정책, 만료 조건이 hash에 포함되어야 한다. preview 또는 payload가 바뀌면 Action Hash도 바뀌고, 기존 approval proof는 더 이상 유효하지 않아야 한다.

3.2 실행 포맷

구분ERC-4337EIP-8141
사용자 검증validateUserOpVERIFY frame
수수료 대납Paymaster + paymasterAndDataPAYMENT frame
액션 실행Smart Account executeEXECUTE frame
제출 경로Bundler → EntryPointprotocol mempool / thin relayer
변환 결과UserOperationFrameTx = VERIFY + PAYMENT + EXECUTE

Smart Account의 검증 로직은 특정 제출 경로에 묶이면 안 된다. Passkey Verifier, Recovery Module, Policy Module은 4337과 8141 양쪽에서 재사용 가능한 형태로 둔다.

3.3 자동결제 / 반복 실행 원칙

자동결제는 서버가 signed action을 저장해두고 나중에 임의로 재해석해 실행하는 구조가 아니어야 한다.

자동결제 실행은 매번 Passkey 재승인을 요구하지 않는다. 대신 최초 등록된 policy가 실행 범위를 제한한다.

항목검증 위치설명
merchantSmart Account / Policy Module승인된 수취인인지 확인
amountCapSmart Account / Policy Module한도를 넘지 않는지 확인
intervalSmart Account / Policy Module실행 주기를 만족하는지 확인
expirySmart Account / Policy Modulepolicy가 만료되지 않았는지 확인
allowedExecutorSmart Account / Policy Module실행 트리거 주체가 허용된 범위인지 확인
nonce / replaySmart Account / Policy Module중복 실행 또는 stale execution 차단

정리하면, 자동결제는 서버 자동 서명이 아니라 사전 승인된 온체인 policy의 반복 실행이다.

3.4 구현 불변조건

  1. Off-chain 준비 단계는 재시도 가능해야 하지만, 재시도가 새로운 사용자 권한을 만들면 안 된다.
  2. Action preview와 서명 대상 digest는 canonical hash로 묶여야 한다.
  3. 사용자 approval proof 없이 생성된 일반 UserOperation은 실패해야 한다.
  4. POLICY_EXECUTE는 owner proof 없이 제출될 수 있지만, 사전 등록된 on-chain policy 검증을 통과해야 한다.
  5. Wallet Directory는 권한 판단자가 아니다.
  6. nonce, expiry, policyId로 replay와 stale approval을 막아야 한다.
  7. Paymaster 권한은 owner approval 권한과 분리한다.
  8. Audit log는 권한 근거가 아니라 사후 추적과 이상탐지 기록이다.

5. Recovery, PAKE, Proof of Non-Custody

5.1 Recovery Passphrase 정책

Recovery passphrase는 이 설계에서 유일하게 password-like한 입력이다. 하지만 PAKE 입력도 아니고, 로그인 비밀번호도 아니며, wallet approval도 아니다. 목적은 User Personal Cloud에 암호문으로 저장된 encrypted recovery backup을 사용자 기기에서 복호화하는 것이다.

Recovery Module은 recovery proof를 approval method 재등록 또는 교체에만 사용해야 한다. Recovery proof가 평상시 결제 승인권이 되면 안 된다.

5.2 PAKE 사용 여부

PAKE 자체가 문제라고 보지는 않는다. 문제는 PAKE 출력 또는 password-derived material이 wallet signing material과 연결되는 사용 방식이다.

이 설계의 목표 구조는 Passkey-first다. PAKE를 wallet approval, account bootstrap, recovery authority의 필수 경로로 사용하지 않는다.

기존 시스템에 PAKE를 남겨야 한다면 아래 범위로 제한한다.

항목허용금지
Account discovery사용자 식별, risk signal, Wallet Directory lookup 보조wallet approval 생성
SessionTenant App 또는 API 세션 생성 보조owner signature, session grant, recovery proof 파생
Password reset인증 record 교체owner 변경, approval method 교체, recovery policy 변경
Recovery flow 진입사용자가 recovery flow를 시작하도록 돕는 보조 인증recovery material 복호화 대행, recovery proof 생성

따라서 PAKE를 유지하려면 auth-only layer로 제한해야 한다. PAKE를 wallet control에 연결하면 R-A1, R-A2, R-A4, R-A8을 동시에 만족하기 어렵다.

5.3 Proof of Non-Custody

사용자 또는 제3자가 아래 명제를 확인할 수 있어야 한다.

Passkey private key는 일반적으로 export가 어렵다. 그래서 이 설계에서 Proof of Non-Custody는 key export가 아니라 독립 서명 시연 + EIP-1271 검증으로 보여준다.

방식설명증명되는 것
독립 challenge signing제3자 verifier가 challenge를 만들고, 사용자가 SDK의 Passkey ceremony로 서명사용자가 서버 없이 approval proof를 만들 수 있음
EIP-1271 검증제3자가 Smart Account의 isValidSignature를 호출해 proof 유효성을 확인Smart Account가 해당 approval method를 인정함
Registered public key 조회Smart Account 또는 verifier registry에서 등록된 Passkey public key 조회서버 DB가 아니라 온체인 검증 기준이 권한의 근거임
Negative test서버 재료만으로 같은 challenge에 대한 valid proof 생성 실패서버 재료만으로 wallet approval을 재현할 수 없음

PoC는 poc.ts로 분리한다.
