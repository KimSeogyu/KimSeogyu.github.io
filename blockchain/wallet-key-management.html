지갑 키 관리는 개인키를 어떻게 만들고, 백업하고, 필요하면 여러 참여자에게 나눌지 정하는 일이다. 한 사람이 쓰는 지갑은 시드 하나에서 키를 파생해 복구를 단순하게 만들고, 여럿이 함께 서명하는 지갑은 체인이 어떤 서명을 검증하는지에서 출발해 방식을 고른다.

왜 필요한가

키를 잃으면 자산을 잃고, 복구 절차가 어긋나면 키가 있어도 같은 주소를 되찾지 못한다. HD 지갑의 가치는 키를 많이 만드는 데가 아니라 복구 가능성과 운영 일관성에 있다. 팀이 운영하는 서비스라면 파생 경로, 백업 절차, 키 권한 경계를 문서로 고정해 두어야 한다.

여러 참여자가 서명해야 하는 지갑에서는 FROST, MuSig2, Threshold ECDSA가 한데 묶여 불리지만 같은 문제를 푸는 기술이 아니다. t-of-n인지 n-of-n인지, 최종 서명이 Schnorr인지 ECDSA인지에 따라 쓸 수 있는 곳이 갈린다. FROST·MuSig2·TSS

작동 방식

HD 지갑: 시드 하나에서 키를 파생한다

  • BIP-39: 12~24개 단어의 니모닉으로 시드를 표현한다.
  • BIP-32: 시드에서 마스터 키, 다시 자식 키를 결정론적으로 파생한다. 일반 파생은 xpub만으로 자식 키를 만들 수 있고, hardened 파생은 부모 개인키가 있어야 한다.
  • BIP-44: 여러 코인과 계정을 나누는 경로 규약이다. 경로는 m / purpose' / coin_type' / account' / change / address_index 꼴이다.
체인경로 예
BTCm/44'/0'/0'/0/0
ETHm/44'/60'/0'/0/0
Aptosm/44'/637'/0'/0'/0' (지갑 구현마다 변형이 있다)

다자 서명: 세 갈래

FROST(Flexible Round-Optimized Schnorr Threshold Signatures)는 그룹 공개키 하나를 두고 개인키를 여러 share로 나눈다. 전체 n명 중 t명이 참여하면 Schnorr 서명 하나를 만든다. key share는 trusted dealer나 DKG로 만들고, DKG에서는 모든 참여자가 public commitment를 똑같이 봐야 한다(broadcast). 서명은 두 라운드를 목표로 하며, 다자 Schnorr에서 nonce를 다시 쓰면 치명적이다. FROST·MuSig2·TSS

MuSig2는 여러 공개키를 aggregate public key 하나로 묶고, 참여자 모두가 협력해 BIP340 Schnorr 서명 하나를 만든다. n-of-n이라 세 명이 키를 묶었다면 세 명이 모두 서명에 참여해야 한다. BIP327도 MuSig2를 t-of-n threshold 서명이 아니라 n-of-n multi-signature로 설명한다. Bitcoin Taproot key path에서는 최종 온체인 모습이 일반 Taproot key spend처럼 보일 수 있다. FROST·MuSig2·TSS

**Threshold ECDSA(TSS)**는 ECDSA 개인키를 share로 나누고, threshold만큼의 참여자가 협력해 일반 ECDSA 서명을 만든다. 결과가 보통의 ECDSA 서명이라 기존 Bitcoin, Ethereum, EVM 주소 체계와 그대로 맞는다. 대신 FROST보다 프로토콜이 무겁다. Paillier, safe prime, 영지식 증명, auxiliary information 같은 구성요소가 함께 따라온다. FROST·MuSig2·TSS

선택지와 트레이드오프

고르는 순서는 체인과 검증식에서 시작한다. FROST·MuSig2·TSS

질문먼저 볼 것
최종 서명이 ECDSA여야 하는가Threshold ECDSA/TSS
Bitcoin Taproot에서 n-of-n이면 되는가MuSig2
t-of-n Schnorr가 필요한가FROST
컨트랙트 계정에서 검증 로직을 직접 정할 수 있는가ECDSA 고정 요구부터 다시 확인
운영자가 signer를 식별하고 제외해야 하는가identifiable abort, key refresh, resharing 지원 여부
프로덕션에 넣는가audit, 유지보수, 릴리스, 보안 문서
  • FROST는 Schnorr 계열이라 ECDSA 주소를 유지해야 하는 EVM custody에 바로 끼워 넣을 수 없다. Schnorr 검증을 쓰거나 컨트랙트가 별도 검증 로직을 둘 수 있는 구조에서 자연스럽다. FROST·MuSig2·TSS
  • “5명 중 3명만 동의하면 된다” 같은 요구는 MuSig2만으로 채울 수 없다. FROST나 Threshold ECDSA를 본다. FROST·MuSig2·TSS
  • Threshold ECDSA는 기존 주소를 유지해야 하는 custody에서 현실적인 선택이지만, 단순한 서명 라이브러리로 보면 안 된다. 네트워크 계층, party index, execution id, aux info, presignature 재사용 방지, key share 보관 정책까지 함께 설계해야 한다. 운영에서는 party discovery, 메시지 전송, timeout, blame, key share 백업, resharing, 장애 복구가 API보다 큰 문제가 된다. FROST·MuSig2·TSS

라이브러리는 기능보다 유지 상태를 먼저 본다. cggmp21은 README 기준으로 key refresh와 identifiable abort를 아직 지원하지 않는다. coinbase/kryptology는 README에서 archived, 더 이상 지원하지 않음, 쓰지 말 것이라고 밝혀 새 프로젝트 후보에서 뺀다. taurushq-io/multi-party-sig는 폭넓게 다루지만 프로덕션에 쓰려면 추가 테스트와 audit가 필요하다고 README에 적혀 있어 연구나 PoC 검토용에 가깝다. FROST·MuSig2·TSS

자주 하는 실수

  • 지갑마다 다른 파생 경로를 문서로 고정하지 않아 복구 사고가 난다.
  • purpose, coin_type, account 단계를 hardened로 두지 않거나 xpub을 필요 이상으로 노출한다.
  • 니모닉을 오프라인이 아니라 클라우드 메모나 스크린샷에 보관한다.
  • 경로 규약 없이 멀티체인으로 넓히거나 테스트넷과 메인넷 경로를 섞는다.
  • MuSig2를 threshold 서명으로 착각한다. MuSig2는 n-of-n이다. FROST·MuSig2·TSS
