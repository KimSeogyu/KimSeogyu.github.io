6. Migration, 실행 계획, 오픈 질문

6.1 Track B / D 연결점

Track B 연결점은 ERC-4337 역할 분리다. Track A의 핵심은 유저 approval authority를 서버에서 제거하는 것이지만, 운영 blast radius를 줄이려면 Bundler, Paymaster, Submitter, owner approval signer도 분리해야 한다.

항목개선 방향
Bundler / SubmitterUserOperation 제출만 담당. owner approval을 만들 수 없어야 함
Paymastersponsor policy와 gas payment만 담당. wallet execution authority를 갖지 않음
Owner approval signer사용자 기기의 Passkey proof 또는 Smart Account policy로 한정
표준 JSON-RPCeth_sendUserOperation, eth_estimateUserOperationGas, eth_getUserOperationReceipt 등 교체 가능한 표면 제공
에러 모델raw revert forwarding이 아니라 구조화된 client error로 정리

Track D 연결점은 Action을 실행 포맷과 분리하는 것이다.

4337 요소8141 대응본 설계에서의 준비
validateUserOpVERIFY framePasskey Verifier를 plug-in 형태로 분리
PaymasterPAYMENT frameFee Policy를 Action과 분리된 object로 관리
Smart Account executeEXECUTE frameAction compiler가 실행 payload를 별도로 생성
Bundlerthin relayer 또는 protocol pathSubmitter를 compiler 이후 단계로 격리
EIP-1271유지 또는 VERIFY와 연계Proof of Non-Custody 검증 경로로 유지

되돌리기 어려운 결정은 특정 signer scheme을 wallet address에 하드코딩하는 것이다. 그래서 Passkey P-256을 쓰더라도 verifier plug-in 구조로 둔다.

6.2 기존 유저 이전 계획

전환 목표는 두 가지다.

단계내용
1. 현재 경로 inventoryK_D 사용처, tx worker 권한, Paymaster signer, Submitter key, recovery path 목록화
2. 기존 Smart Account capability 확인verifier module 추가, owner mutation, recovery module 추가, EIP-1271 경로, upgrade path 확인
3. Passkey approval method 등록사용자가 기존 wallet에 Passkey owner 또는 verifier binding 등록
4. Recovery Module 설정User Personal Cloud encrypted backup 또는 기존 기기 approval 기반 recovery path 설정
5. 자동결제 policy 이전signed action 보관 방식이 있다면 Policy Module 기반으로 전환
6. 서버 대리 서명 폐기K_D 기반 owner approval 경로 비활성화, 접근 권한 회수, 폐기 로그 기록
7. 검증proof 없는 UserOperation 실패, Passkey proof 기반 실행 성공, policy 범위 밖 자동결제 실패 테스트

기존 Smart Account가 verifier 교체나 module 추가를 지원하지 않으면 주소 유지와 완전한 non-custodial 전환을 동시에 달성하기 어렵다. 이때 fallback은 아래처럼 나눈다.

fallback조건단점
Wrapper / delegation account기존 account가 제한된 delegation 또는 module call을 지원구조가 복잡하고 사용자 설명이 어려움
Migration smart account기존 주소가 새 account로 권한을 위임할 수 있음기존 account 기능에 의존
신규 주소 + balance migration기존 컨트랙트에서 verifier 교체가 불가능주소 연속성 포기. 사용자 커뮤니케이션 필요

주소 유지를 위해 서버 수탁 경로를 억지로 유지하면 안 된다. 주소 유지와 non-custodial 전환이 충돌하면, 충돌 자체를 명시하고 사용자/법무/감사 관점의 선택지를 분리해야 한다.

6.6 R-A2, R-A5, 서버사이드 자동화의 긴장

세 요구가 충돌하는 이유는 현재 구조에서 K_D가 너무 많은 역할을 하기 때문이다.

이 설계에서는 세 역할을 분리한다.

요구해결 방향
R-A2 서버 대리 서명 제거서버가 owner approval을 만들 수 없게 함. wallet execution은 action-bound Passkey proof 또는 on-chain policy로만 가능
R-A5 멀티 디바이스 유지새 기기 등록은 기존 기기 approval 또는 recovery proof 필요. Wallet Directory는 wallet address 조회만 담당
서버사이드 자동화범용 서버 서명 대신, 사용자가 사전 승인한 on-chain policy 범위 안에서만 실행

R-A5를 “계정 세션만으로 지갑 권한이 완전히 회복된다”로 해석하면 non-custodial과 충돌한다. 그래서 이 설계에서는 아래처럼 재해석한다.

이건 UX 손실이다. 하지만 서버 수탁 없이 멀티 디바이스와 자동화를 유지하려면 필요한 trade-off라고 본다.

6.7 가장 약한 지점

가장 약한 지점은 기존 Smart Account가 verifier swap / module 추가를 지원하지 않는 경우다.

이 경우 “기존 주소 유지”와 “완전한 non-custodial 전환”을 동시에 만족시키기 어렵다. wrapper account나 migration smart account로 완화할 수는 있지만, 둘 다 기존 컨트랙트 capability에 의존한다. capability가 없으면 신규 주소 전환까지 열어둬야 한다.

실무에서는 첫 2주 안에 아래를 먼저 검증해야 한다.

두 번째 약한 지점은 recovery passphrase UX다. K-retail 사용자에게 high-entropy recovery passphrase는 어려울 수 있다. Guardian을 넣으면 UX는 좋아지지만, guardian threat model이 별도로 필요하다. 그래서 본 설계에서는 guardian을 핵심 경로가 아니라 선택적 보완 경로로 둔다.

6.8 최종 요약

핵심 변화는 다섯 가지다.

결론적으로 WaaS는 계속 지갑 인프라를 운영할 수 있다. 다만 사용자 자산 이동에 필요한 최종 승인 권한은 서버가 아니라 사용자 기기와 Smart Account 정책에 남아야 한다.

A.4 자동결제

자동결제는 두 단계로 나눈다.

  1. 사용자가 자동결제 규칙을 Passkey로 사전 승인하고, Smart Account의 Policy Module에 등록한다.
  2. 결제 시점이 되면 WaaS scheduler 또는 authorized tenant backend가 실행을 트리거한다. Smart Account는 매 실행마다 policy 범위를 검증한다.

A.5 시나리오별 핵심 차이

시나리오권한 근거서버 역할최종 검증
신규 지갑 생성새 기기 Passkey approval proofflow 생성, counterfactual address 결정, UserOperation 제출Smart Account / Passkey Verifier
두 번째 기기 등록기존 기기 Passkey approval proof새 기기 등록 flow 생성, 기존 기기 승인 요청, 제출Smart Account / Passkey Verifier
지갑 복구recovery proof + 새 기기 Passkey public keyrecovery flow 생성, proof 제출, UserOperation 제출Smart Account / Recovery Module
자동결제 등록사용자 Passkey approval proofpolicy 등록 Action 생성, 제출Smart Account / Passkey Verifier
자동결제 실행사전 등록된 on-chain policy실행 트리거, UserOperation 제출Smart Account / Policy Module

정리하면, WaaS는 계속 flow를 진행하고 제출을 담당한다. 하지만 사용자 자산 이동에 필요한 권한 근거는 사용자 기기의 approval proof, recovery proof, 또는 Smart Account에 사전 등록된 policy여야 한다.
