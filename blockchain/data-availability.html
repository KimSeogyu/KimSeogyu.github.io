데이터 가용성

데이터 가용성

2026년 11월 19일

  • Blockchain
  • Celestia
  • Data-Availability

블록 헤더의 해시가 맞아도 본문을 실제로 받을 수 있다는 보장은 없다. 데이터 가용성은 이 빈틈을 다루는 문제이고, Celestia는 전체를 내려받는 대신 2D 이레이저 코딩과 무작위 샘플링으로 확률적으로 충분한 검증을 택했다.

왜 필요한가

“해시가 맞다”와 “데이터를 실제로 받을 수 있다”는 다른 문제다. 생산자가 헤더의 해시만 공개하고 본문 일부를 숨기면 무결성 검증은 통과해도, 데이터를 다시 만들거나 상태를 검증할 수는 없다. 해시 검증은 일관성만 보장하고 가용성은 보장하지 않는다.

전형적인 공격이 data withholding이다. 유효한 헤더와 루트를 퍼뜨리고 본문 일부를 숨기면, 노드는 헤더를 받아들이고도 상태를 다시 검증할 수 없어 체인이나 롤업의 신뢰가 약해진다. 그래서 루트 검증에 더해, 무작위 샘플을 실제로 요청해 응답 가능성을 확인하는 데이터 가용성 샘플링(DAS)이 필요하다. 샘플이 충분히 회수되면 전체 가용성을 확률적으로 보장하고, 일부가 숨겨져 있으면 높은 확률로 탐지한다.

작동 방식

Celestia에서 블록 데이터는 바로 EDS가 되지 않는다. 먼저 ODS(Original Data Square)를 만들고, 그다음 확장한다.

트랜잭션을 종류별로 나눈 뒤 share로 쪼개고, 네임스페이스 순으로 정렬한 다음, 패딩으로 2의 거듭제곱 크기 정사각형(ODS)을 만든다. 일반 트랜잭션과 PFB(PayForBlob)는 compact share에, blob 데이터는 sparse share에 따로 담아 배치 효율을 높인다. Celestia는 네임스페이스 단위 검증을 지원하므로, share를 놓을 때의 정렬 규칙이 중요하다. 이 전처리가 이후 샘플링과 증명의 효율을 정한다. max square size는 네트워크와 메모리 한계에 맞춰 관리하고, 패딩 비율이 높으면 배치 정책을 다시 보며, 네임스페이스 정렬 규칙을 바꿀 때는 하위 호환을 따진다.

ODS는 행과 열 양쪽으로 2D 리드-솔로몬 확장되어 EDS(Extended Data Square)가 된다. EDS는 네 사분면이다. Q1은 원본(ODS), Q2는 행 패리티, Q3는 열 패리티, Q4는 행과 열 패리티다. 일부가 빠져도 복구할 수 있고, 샘플링과 복구를 같이 할 수 있다. 2D 인코딩은 단순 복제보다 저장 효율이 높고, 누락 패턴이 생겨도 복구될 가능성이 크며, DAS와 함께 쓸 때 탐지와 복구의 균형이 좋다. Q1부터 Q4까지의 역할은 설계 문서에서 팀 공통 언어로 고정해 둔다.

flowchart TD
    TX[트랜잭션 분류] --> SH[Share 분할]
    SH --> NS[네임스페이스 정렬]
    NS --> PAD[패딩]
    PAD --> ODS[ODS]
    ODS --> EDS[2D 리드-솔로몬 확장 EDS]
    EDS --> DAS[DAS 샘플 검증]

라이트 노드는 블록 전체를 받지 않고 EDS 좌표를 무작위로 고른 뒤, 샘플과 증명을 요청해 검증한다. 충분한 샘플이 성공하면 블록 가용성을 높은 확률로 받아들인다. 공격자가 데이터 절반을 숨겼다면 샘플 하나가 숨긴 곳을 피할 확률은 1/2이고, 독립 샘플 n개가 모두 피할 확률은 (1/2)^n이다. 샘플을 조금만 늘려도 탐지 실패는 급격히 줄어든다. 기본 샘플 수는 고정값(예: 16)에서 시작하지만 정답이 아니다. 샘플을 늘리면 탐지 확률과 함께 네트워크와 지연 비용도 늘고, 줄이면 반대다.

검증은 세 장치의 조합이다. EDS가 복구 가능성을, DAS가 가용성을, 네임스페이스 머클 트리(NMT)가 필요한 부분만 검증하는 효율을 맡는다. 순서는 헤더를 받고, 무작위 샘플과 증명을 요청해 루트와 맞춘 뒤, 샘플 정책을 채우면 가용하다고 받아들이는 것이다. 실제로 중요한 것은 수학보다 노드 사이 운영 파라미터의 일관성이다. 피어 품질이 나빠져 샘플링 실패율이 치솟거나, 노드마다 저장 윈도우 정책이 다르거나, 검증 파라미터를 바꿔 노드 사이 판단이 갈리는 것이 위험이다.

저장도 시간에 따라 달리 한다. celestia-node의 store/file 패키지가 이 정책을 맡는다. 최근 블록은 원본과 Q4를 함께(ODSQ4, EDS의 약 1/2) 두어 샘플링과 복구 계산을 줄이고, 오래된 블록은 원본만(ODS, 약 1/4) 둬 디스크를 아낀다. 접근자는 ODS, q4, ODSQ4이고, 파일 포맷 메타데이터는 headerV0, 리드-솔로몬 인코더 캐시는 codecCache다. Q4는 lazy loading으로 시작 지연을 줄이고, 파일 크기나 해시 검증에 실패하면 바로 격리하며, 인코더 캐시 적중률을 지켜봐 CPU 급등을 막는다. EDS 생성 실패는 인코딩 문제와 입력 데이터 문제를 나눠 로깅하고, 복구 경로 테스트는 정기적으로 돌린다. 가용성 윈도우 경계를 분명히 정해 두는 것이 이 전략의 전제다.

선택지와 트레이드오프

저장내용용량쓰는 구간
ODS원본 사각형(Q1)EDS 대비 약 1/4오래된 블록, 아카이브
ODSQ4ODS와 Q4EDS 대비 약 1/2최근 블록의 샘플링과 복구
EDS 전체Q1부터 Q4기준상시 전부 저장하지 않음

DAS는 완전 검증이 아니라 저비용 확률 검증이다. 고정값에 의존하기보다, 실제 네트워크 품질과 공격 가정에 맞춰 샘플 정책을 조정한다. 운영에서 보는 지표는 샘플 요청 성공률과 재시도율, 응답 지연 p95/p99, 블록 크기 구간별 실패율, 피어별 불응 비율이다.

실제 적용

라이트 노드는 샘플 정책만 채우면 블록을 가용하다고 받아들인다. 같은 네트워크라도 피어 품질이 떨어지면 실패율이 치솟고, 저장 윈도우가 노드마다 다르면 최근 블록을 ODSQ4로 둘지 ODS만 둘지가 어긋난다. 검증 파라미터를 바꿀 때도 노드 사이 판단이 갈리지 않게 먼저 맞춘다. store/file은 단순 파일 저장소가 아니라, DAS와 복구 비용을 운영 가능한 수준으로 맞추는 스토리지 전략 계층이다.
